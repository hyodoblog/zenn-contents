社内向けのサイトを Vercel に置いています。案件ごとの開発費用や体制が載っているので、外に出したくない種類のデータです。公開したときに noindex を入れて、そこでタスクは閉じられました。278 日後に `curl` を叩いたら、本番だけ 200 が返ってきました。

結論から言うと、原因は 2 つでした。Vercel の Deployment Protection は初期設定だと本番ドメインを守りません。そして `robots.txt` の `Disallow` は、自分で入れた noindex を読ませなくします。どちらも設定は入っていて、どちらも意図した範囲で動いていました。誰も範囲を読んでいませんでした。

この穴は AI が空けたものではありません。人が書いたコミットです。ただ、同じ依頼文をエージェントに渡すと、同じものがもっと速く出てきます。そこが怖いところだと考えて、AI エージェントで社内アプリを作るときの注意点としてまとめ直しました。記事の後半にチェックリストを付けています。

:::message
自社の社内向けシステムを直した記録です。プロダクト名・ドメイン・チーム名は伏せ、URL やプロジェクト名は一般的な名前に置き換えています。ステータスコードと日数は、実際に手元で測った値です。
:::

## つくっていたもの

- **アプリ**: Next.js 16（App Router）
- **ホスティング**: Vercel（GitHub 連携で `main` へのマージが本番反映）
- **コンテンツ**: ヘッドレス CMS
- **中身**: 案件ごとの開発費用・期間・担当領域・課題

社外に出す想定のない情報です。つまり、URL を知られた時点で困ります。

## 事件発生：本番だけ 200 が返ってくる

別件で認証を足そうとして、まず現状を測りました。Vercel は 1 つのデプロイに複数の URL を配ります。全部叩いてみます。

```bash
# 本番のカスタムドメイン
curl -s -o /dev/null -w "%{http_code}\n" https://example.com/

# Vercel が配る本番の生成 URL
curl -s -o /dev/null -w "%{http_code}\n" https://my-tool-acme.vercel.app/

# ブランチ URL
curl -s -o /dev/null -w "%{http_code}\n" https://my-tool-git-main-acme.vercel.app/
```

結果です。

| URL の種類 | ステータス | 中身 |
| --- | --- | --- |
| 本番のカスタムドメイン | 200 | 全部読める |
| 本番の生成 URL | 302 | Vercel の SSO へ飛ぶ |
| ブランチ URL | 302 | Vercel の SSO へ飛ぶ |

> 生成 URL もブランチ URL も守られているなら、本番も守られているはずでした。

違いました。守られていなかったのは、いちばん人に配っている URL だけです。

ここで 1 回転びました。最初は `<project>.vercel.app` という形で叩いていて、200 が返ってきたので「生成 URL も丸見えだ」と判断しています。実際にはスコープ名が抜けていて、**まったく別の人のサイトを叩いていました**。返ってきた HTML の `<title>` を見て気付きます。

```bash
curl -s https://my-tool.vercel.app/ | grep -o "<title>[^<]*</title>"
# <title>Particles Webpage</title>   ← 誰のものか分からないサイト
```

ステータスコードだけ見て判断すると、こういう間違え方をします。**測るなら、中身が自分のものかまで見ます。**

## 敗北：noindex を鍵だと思っていた

入っていたのは、この 2 つです。

```ts:app/layout.tsx
export const metadata: Metadata = {
  robots: {
    index: false,
    follow: false,
  },
}
```

```ts:app/robots.ts
export default function robots(): MetadataRoute.Robots {
  return {
    rules: {
      userAgent: "*",
      disallow: "/",
    },
  }
}
```

どちらも正しく動いていました。本番の HTML には `<meta name="robots" content="noindex, nofollow"/>` が入っていて、`/robots.txt` も `Disallow: /` を返します。

**「検索に出ない」と「見られない」は、別のことです。** noindex は行儀のいいクローラーへのお願いであって、鍵ではありません。URL を知っている人は普通に全部読めます。

さらに悪いことに、この 2 つは噛み合っていませんでした。Google のドキュメントは、noindex が効く条件として、そのページが `robots.txt` でブロックされていないことを挙げています。クロールを止めると、クローラーは noindex に到達しません。外部にリンクが 1 本でもあれば、URL だけが検索結果に載ることがあります。

——**鍵をかけたつもりで、鍵の場所を書いた紙を貼っていただけでした。**

### 依頼の枠が、そのまま成果物の枠になっていた

このコードを入れたコミットを見にいきました。メッセージがすべてを説明していました。

```bash
git log --diff-filter=A --format="%h %ad %s" --date=short -- apps/web/app/robots.ts
# b647491 2025-12-05 feat: SEO対策のために、robotsメタ設定を追加し、robots.txtファイルを作成
```

**「SEO 対策のために」**。依頼も実装も、最初から検索の話でした。アクセス制御の話をした人が、どこにもいません。だから成果物にも入っていません。仕事としては、依頼どおりに正しく終わっています。

念のため確認すると、このリポジトリの 49 コミットのうち、AI との共著になっているのは 1 件だけです。今回私が入れた修正のコミットです。

```bash
git log --grep="Co-Authored-By: Claude" --oneline | wc -l   # 1
git log --oneline | wc -l                                   # 49
```

つまりこれは、人が人の依頼で空けた穴です。それでもこの記事を AI エージェントの注意点として書いているのは、渡す依頼文が同じなら、返ってくる答えも同じだからです。**しかも、もっと速く、もっと自信を持って返ってきます。**

## なぜ AI エージェントだとこの穴が空くのか

理由の前に、前提を数えておきます。穴が空いたリポジトリの AI 共著は 1 件だけでした。ところが、いま動いている別の業務システムのリポジトリでは比率がまるで違います。

```bash
git log --grep="Co-Authored-By: Claude" --oneline | wc -l   # 82
git log --oneline | wc -l                                   # 380
ls .claude/worktrees | wc -l                                # 18
ls .claude/worktrees | grep -c '^codex-'                    # 15
```

380 コミットのうち 82 コミットが AI との共著です。作業用の worktree は 18 個中 15 個が `codex-` で始まります。**今回の穴は人が空けました。これから作るものは、この比率で作られます。**

その前提で、今回の件と直した作業から、再現しそうな理由を 5 つ挙げます。

### 1. エージェントは枠の外を疑わない

「SEO 対策として noindex を入れて」と頼めば、noindex が入ります。それ以上は入りません。人間の同僚なら、案件の費用が並んだ画面を見て「これ社内情報じゃないですか」と聞き返すことがあります。この聞き返しが、エージェントには構造的に起きにくいです。指示の枠がうまいほど、枠の外は静かになります。

### 2. リポジトリのどこにも「社内向け」と書いていなかった

エージェントはリポジトリを読んで前提を作ります。そこで、このリポジトリに何が書いてあるか調べました。

```bash
ls CLAUDE.md AGENTS.md .cursor
# どれも存在しない

grep -ncE "社内|公開範囲|非公開|認証" README.md
# 0
```

`CLAUDE.md` も `AGENTS.md` もありません。README を検索しても、公開範囲に触れた行は 1 つも出ませんでした。それどころか、末尾にはこう書いてあります。

> このプロジェクトのコードは公開されています。

ライセンスの節にある、コードについての一文です。ただ、リポジトリを読んで文脈を組み立てる側からすると、**このプロジェクトは公開前提だという結論に達します**。書いていない前提は、存在しない前提です。

### 3. 完了条件がローカルで閉じている

ビルドが通り、lint が通り、テストが緑になれば、エージェントの仕事は終わります。ここまでは全部ローカルで完結します。一方、**本番の URL に外から到達できるかどうかは、リポジトリの中に情報がありません**。誰かが明示的に頼まない限り、`curl` を叩く工程は発生しません。

### 4. エージェントが読むドキュメントも間違える

今回の修正で実際に踏みました。Next.js 16 では `middleware.ts` が `proxy.ts` にリネームされています。その設定オブジェクトの名前を、私が参照したプラグイン同梱のドキュメントは `proxyConfig` と書いていました。公式は `config` のままです。

```ts:proxy.ts
// 公式（Next.js 16）はこちら
export const config = {
  matcher: "/about/:path*",
}
```

名前を間違えると `matcher` は読まれず、全リクエストで `proxy` が動きます。今回はたまたま安全側に転びますが、意図とは違う挙動です。**エージェントに与える参考資料が、エージェントの間違いの原因になります。**

### 5. モデルの知識と、目の前のバージョンがずれる

`middleware` から `proxy` への変更は Next.js の v16.0.0 です。学習時点が古いモデルは `middleware.ts` を書きます。非推奨なので動きはします。動くので気付きません。**バージョンを指定して、公式ドキュメントで裏を取らせる**のが対策になります。

なお、テンプレートから起こしたリポジトリだと、この種の前提はまとめて複製されます。今回のリポジトリも `package.json` の `name` が雛形の名前のままでした。1 か所の穴が、そのまま N 個に増えます。

## 転機：設定名ではなく適用範囲を読む

Vercel 側の設定は、実は入っていました。ブランチ URL が SSO へ飛んだのがその証拠です。リダイレクト先を見ます。

```bash
curl -sI https://my-tool-git-main-acme.vercel.app/ | grep -i location
# location: https://vercel.com/sso-api?url=...&nonce=...
```

Vercel Authentication が効いています。効いているのに本番が公開されている。ドキュメントを読み直したら、そう書いてありました。

保護の設定は、**方式**と**範囲**の 2 軸に分かれています。範囲のほうが問題でした。

| 保護範囲 | 何を守るか | プラン |
| --- | --- | --- |
| Standard Protection | 本番ドメイン以外のすべて | 全プラン |
| All Deployments | 本番ドメインを含むすべて | Pro / Enterprise |

初期値の Standard Protection は、**本番ドメインを対象から外します**。名前が「標準」なので、全体にかかるものだと読んでいました。

方式のほうも、プランで使えるものが変わります。

| 方式 | プラン |
| --- | --- |
| Vercel Authentication | 全プラン |
| Password Protection | Enterprise、または Pro で月 150 ドルのアドオン |
| Trusted IPs | Enterprise |
| Passport | Enterprise |

Hobby プランでは Standard Protection しか選べません。つまり **Hobby に置いた社内ツールの本番ドメインは、Vercel の機能では閉じられません**。アプリ側で塞ぐ必要があります。

### 推測できる URL が 3 種類ある

「URL を知られなければ大丈夫」は、どのくらい成り立つのか。ドキュメントに URL の組み立て方が載っています。

| 種類 | 形 | 推測 |
| --- | --- | --- |
| コミット URL | `<project>-<9 文字のハッシュ>-<scope>.vercel.app` | 難しい |
| ブランチ URL | `<project>-git-<branch>-<scope>.vercel.app` | 容易 |
| CLI・本番の URL | `<project>-<scope>.vercel.app` | 容易 |

ランダムな部分があるのはコミット URL だけで、9 文字です。ブランチ URL は、プロジェクト名とチーム名と `main` が分かれば組み立てられます。GitHub の Organization 名とリポジトリ名から素直に付けていれば、外から当てられます。

なお、プレビューには Vercel が `x-robots-tag: noindex` を自動で足します。**本番には足しません**。手元でも確認できました。

```bash
curl -sI https://my-tool-git-main-acme.vercel.app/ | grep -i x-robots-tag
# x-robots-tag: noindex

curl -sI https://example.com/ | grep -i x-robots-tag
# （何も出ない）
```

## proxy.ts で Basic 認証を書く

プランを上げる前に、アプリ側で閉じました。移行用の codemod があります。

```bash
npx @next/codemod@canary middleware-to-proxy .
```

codemod が変えるのはファイル名と関数名です。設定オブジェクトは `config` のままです。

```ts:proxy.ts
export function proxy(request: NextRequest): NextResponse {
  const { BASIC_AUTH_USER: user, BASIC_AUTH_PASSWORD: password } = env

  if (!user || !password) {
    // 設定漏れで社内情報が公開されるより、落ちて気付くほうが安全
    if (env.NODE_ENV === "production") {
      return new NextResponse("Basic authentication is not configured", {
        status: 503,
      })
    }
    return NextResponse.next()
  }

  if (isValidCredentials(request.headers.get("authorization"), user, password)) {
    return NextResponse.next()
  }

  return new NextResponse("Authentication required", {
    status: 401,
    headers: {
      "WWW-Authenticate": 'Basic realm="Internal", charset="UTF-8"',
    },
  })
}
```

`isValidCredentials` は `atob` でヘッダーを開いて突き合わせるだけなので省きました。1 点だけ、**パスワードに `:` が入る場合があるので、最初の `:` でのみ分割します**。`split(":")` で受けると、そこから先が落ちます。

### matcher を書かないほうが安全なこともある

`matcher` を書かないと、`proxy` は静的ファイルや `public/` を含む全リクエストで動きます。重いので、普通は除外パターンを書きます。公式にもこの形が載っています。

```js
export const config = {
  matcher: [
    "/((?!api|_next/static|_next/image|favicon.ico|sitemap.xml|robots.txt).*)",
  ],
}
```

パフォーマンスの話としては妥当です。ただし**認証のために貼ると、`api` が認証の外に出ます**。社内データを返す API があれば、そこだけ素通しになります。この形はエージェントが最初に出してくる定型でもあるので、認証用途では特に注意が要ります。

今回は全部を守りたいので、`matcher` を書かないことにしました。速度より穴を作らないほうを取ります。

関連して、公式に書いてある挙動を 2 つ拾っておきます。

- `_next/data` は除外パターンに入れても `proxy` が走る。ページを守ってデータ経路を忘れる事故を防ぐため、意図的にそうしている
- Server Functions は独立したルートではないため、`matcher` の変更やリファクタで対象から静かに外れることがある。公式は `proxy` だけに頼らず、各 Server Function の中でも確認するよう勧めている

### 塞いだつもりを、外から叩いて確かめる

書いたら測ります。`next build` して `next start` し、`curl` を並べました。

| リクエスト | 期待 | 結果 |
| --- | --- | --- |
| 認証情報なしで `/` | 401 | 401 |
| パスワードを間違えて `/` | 401 | 401 |
| 正しい認証情報で `/` | 200 | 200 |
| 正しい認証情報で詳細ページ | 200 | 200 |
| 認証情報なしで `/robots.txt` | 401 | 401 |
| 認証情報なしで `public/` の画像 | 401 | 401 |
| 本番かつ環境変数が未設定 | 503 | 503 |
| 本番かつ環境変数が空文字 | 503 | 503 |
| 開発かつ環境変数が未設定 | 200 | 200 |

画像まで 401 になっているかは、目視では分かりません。`curl` で 1 本ずつ叩くのが早いです。

最後の 3 行は、環境変数を入れ忘れたときの挙動です。素通しにすると、設定漏れがそのまま公開につながります。本番では 503 で閉じ、ローカルだけ素通しにしました。空文字で無効化されないよう、`@t3-oss/env-nextjs` の `emptyStringAsUndefined` も有効にしています。

なお noindex の 2 つは消していません。認証が外れたときの保険として残しています。

## 社内アプリをAIエージェントと作るときのチェックリスト

同じ穴を踏まないために、確認項目へ落としました。全 66 項目は分量があるので、[GitHub の詳細版](https://github.com/hyodoblog/zenn-contents/blob/main/docs/internal-app-checklist/checklist.md)へ分けています。ここには、今回いちばん効いたものだけ置きます。

- [ ] `CLAUDE.md` か `AGENTS.md` に「このアプリの公開範囲」を書いた
- [ ] README の記述が、公開範囲と矛盾していない
- [ ] SEO 対策とアクセス制御を、別のタスクとして依頼した
- [ ] 本番のカスタムドメインを、認証なしで `curl` して 200 が返らないことを確認した
- [ ] 生成 URL とブランチ URL でも同じ確認をした
- [ ] 叩いた URL が本当に自分のサイトか、`<title>` まで見た
- [ ] Deployment Protection の**範囲**が、本番ドメインを含むか確認した
- [ ] `matcher` の除外パターンが、認証の置き場所と矛盾していない
- [ ] 環境変数が未設定のとき、本番が素通しではなく閉じる側へ倒れる
- [ ] 静的ファイルと `public/` の画像にも認証がかかることを確認した
- [ ] `.env` 系のファイルが Git に入っていない（`git ls-files` で見る）
- [ ] 本番へ反映したあと、もう一度ステータスコードを測った

## 学び

### 1. 「検索に出ない」と「見られない」を分ける

noindex はクローラーへのお願いで、アクセス制御ではありません。しかも `robots.txt` の `Disallow` と併用すると、noindex 自体が読まれなくなります。**検索対策を security の欄に書いた時点で、その表は間違っています。**

### 2. 公開範囲は、コードではなくリポジトリに書く

このリポジトリには `CLAUDE.md` も `AGENTS.md` もなく、README にも公開範囲の記述がありませんでした。人も AI も、書いていないことは読めません。**エージェントに渡す文脈は、実装より先に整える対象です。**

### 3. 設定名ではなく適用範囲を読む

Standard Protection は「標準」という名前ですが、本番ドメインを守りません。有効になっている画面を見て安心したのが敗因でした。**オンとオフだけ見て、どこにかかるかを見ないと、設定は入っているのに穴が開きます。**

### 4. 塞いだつもりの穴は、外から叩く

ブラウザで見ると、認証が効いているかは分かります。画像や `robots.txt` まで効いているかは分かりません。今回は 9 行の `curl` で状態が確定しました。**画面で確かめた安全は、まだ測っていない安全です。**

### 5. 環境変数の入れ忘れは、閉じる側に倒す

認証情報が空なら認証を飛ばす実装は、書きやすくて危ないです。設定漏れが公開へ直結します。**閉じて落ちれば誰かが気付きますが、開いて動くと誰も気付きません。**

## おわりに

278 日のあいだ、社内情報が載ったページは誰でも読める状態でした。幸い外部からのリンクはなく、検索結果にも出ていません。とはいえ、無事だった理由が「たまたま誰も URL を組み立てなかったから」なのは、あまり気分のいいものではありません。

Vercel の設定も noindex も、入っていました。動いてもいました。足りなかったのは、それぞれがどこまでを守るのかを読むことでした。

そして、その「読む」を誰がやるのかは、エージェントを使うほど曖昧になります。実装が速くなった分、**依頼の枠を決める側の責任が重くなった**という話だと考えています。

Basic 認証はここまでで、人が増えて役割が分かれると足りなくなります。その先は続きの 2 本に書きました。
