今回は、LINE ミニアプリで「LINE の配信を受け取った会員が一斉に開いて、ルーレットを回す」ときに、どこまで耐えられるかを負荷試験で測り、直した記録を紹介します。

[技術構成編](https://zenn.dev/yoshinani_dev/articles/a7d3e19c4b2f60)で紹介した、Next.js（Vercel）+ Supabase + Prisma 7 の構成です。リリース直前に「大量の同時アクセスに耐えられる構成になってる？」と聞かれて、正直に答えると「確かめていません」だったので、測るところから始めました。

最初の試験では、100 人が同じ瞬間にルーレットを回すと 4% しか成功しませんでした。最終的には、1 万人が 5 分の間に来ても全員回せるところまで直しています。

:::message
本記事は業務システムの開発に伴走した記録です。クライアント名・プロダクト名は伏せ、ドメイン名は架空の値に置き換えています。数字はすべて検証環境（Supabase の Micro）で測ったものです。
:::

## 構成と、心配していたところ

- ミニアプリと管理画面：Next.js 16（App Router）on Vercel（Fluid compute）
- DB：Supabase（Postgres）。アプリからは接続プール（トランザクションモード）経由
- ORM：Prisma 7 + `@prisma/adapter-pg`（Driver Adapters）
- 抽選：会員 1 人 1 回のルーレット。景品ごとに在庫（本数上限）がある

LINE の配信はリンク付きで、押すとそのままルーレットの画面が開きます。つまり配信の直後は、会員が「開く → 回す」をほぼ同時に行います。しかもこの DB は別の決済システムと共用しているので、ミニアプリが詰まると、そちらまで止まる可能性がありました。

## 負荷試験のスクリプト

何度でも同じ条件で流せるように、リポジトリにスクリプトとして置きました。やっていることは 4 つです。

1. 試験用の開催回（在庫たっぷり）と、試験用の会員を N 人作る
2. **開く**：会員ごとにセッション Cookie を作り、ミニアプリの画面を HTTP で開く
3. **回す**：本番と同じ抽選の関数を、DB に向けて実行する
4. 作った会員と開催回を消す

セッションは HS256 の JWT を Cookie に入れているだけなので、検証環境の署名鍵があればスクリプトから作れます。

```ts:loadtest/roulette-spike.ts（抜粋）
function sessionCookie(lineUserId: string, secret: string): string {
  const encode = (value: object) =>
    Buffer.from(JSON.stringify(value)).toString("base64url")
  const iat = Math.floor(Date.now() / 1000)
  const header = encode({ alg: "HS256" })
  const payload = encode({ sub: lineUserId, onboarded: true, iat, exp: iat + 3600 })
  const signature = createHmac("sha256", secret)
    .update(`${header}.${payload}`)
    .digest("base64url")
  return `session=${header}.${payload}.${signature}`
}
```

「回す」は子プロセスに分けています。アプリは 1 インスタンスにつき 1 つの接続プールを持つので、子プロセスを 25 個立てれば「Vercel のインスタンス 25 台ぶん」の接続の持ち方を再現できます。

```ts:loadtest/roulette-spike.ts（抜粋）
const child = fork(process.argv[1], ["--worker"], {
  execArgv: process.execArgv, // tsx のまま子プロセスを起動する
  env: process.env,
})
child.send({ eventId, assignments, startAt })
```

本番の DB は決済と共用しているので、**本番には向けられない**ようにしています。接続先が本番のプロジェクトか、開く先が本番のドメインなら、何もせずに止まります。

### 最初に間違えたこと

最初の試験で「開く：全員成功」と出たのですが、実は全員 404 の画面を開いていました。日本語の画面はパスに `/ja` を付けない作りだったのに、スクリプトが `/ja/roulette` を開いていたためです。Next.js は 404 でも画面の骨組みを 200 で返すことがあるので、ステータスだけでは気付けませんでした。

それからは、応答の本文に試験用の開催回の名前が入っていなければ成功と数えないようにしています。

```ts
const html = await res.text()
const result =
  res.status === 200 && !html.includes(eventName) ? "200_other_page" : String(res.status)
```

もう 1 つ、1 万人を同時に開く試験の直後は、次の試験の「開く」がすべて一瞬で失敗しました。手元の PC から出せる接続が尽きていたようで、測れていたのはサーバーではなく PC の限界でした。PC 1 台から測れるのは 1 万人あたりまでだと思います。

## 最初の結果

検証環境（Supabase の Micro）で流した最初の結果です。

| 条件 | 画面を開く | ルーレットを回す |
| --- | --- | --- |
| 100 人が同じ瞬間に回す | 67% | **4%** |
| 1 万人を 3 分に散らす（1 秒に 55 人） | 100% | **8.4%** |

まず抽選のロックを直したところ（後述の 2）、1 万人を 3 分の「回す」だけを流す試験では 97.9% まで上がりました。ただ、「開く」も一緒に流すと、1 万人を 10 分に散らしても回せたのは 72% でした。

失敗のほとんどは次のエラーでした。

```
(EMAXCONN) max client connections reached, limit: 200
```

DB 本体の接続上限（Micro は 60）ではなく、**接続プール（Supavisor）の受付上限 200** に当たっています。DB 自体には余裕がありました。

## 原因：インスタンスの数 × 1 台あたりの接続数

抽選のロックを直したあとの構成で、1 秒あたりの人数を 5・10・15・20・30 人と変えて、それぞれ 1 分ずつ流すと、どれも全員成功しました。一方で 1 秒に 17 人を 10 分続けると 72% でした。限界を決めていたのは「1 秒あたりの人数」より「混雑が続く時間」でした。

Vercel は混むほどインスタンスを増やします。Prisma の `adapter-pg` に接続文字列だけを渡すと、`pg` の既定値（1 インスタンス最大 10 本、使っていない接続を 10 秒保持）になります。混雑が続くとインスタンスが増え、その合計が受付上限に届く、という形でした。

## 直したこと

### 1. 接続プールを明示的に作り、1 台あたりの本数を絞る

```ts:packages/schema/src/client.ts（抜粋）
import { PrismaPg } from "@prisma/adapter-pg"
import { attachDatabasePool } from "@vercel/functions"
import { Pool } from "pg"

function createClient(): PrismaClient {
  const pool = new Pool({
    connectionString: process.env.DATABASE_URL,
    max: poolMax(), // 既定 3。環境変数 DATABASE_POOL_MAX で変えられる
    idleTimeoutMillis: 5_000,
    connectionTimeoutMillis: 30_000,
  })
  // インスタンスが一時停止する前に、空いた接続を閉じ切るまで待たせる（Vercel 上でのみ働く）
  attachDatabasePool(pool)
  return new PrismaClient({ adapter: new PrismaPg(pool) })
}
```

`attachDatabasePool` は `@vercel/functions` の関数で、Fluid compute のインスタンスが止まる前に、使っていない接続を閉じ切るまで待たせてくれます。ソースを読むと、Vercel 上（`VERCEL_URL` と `VERCEL_REGION` がある環境）でしか動かないので、ローカルやビルドでは何もしません。

1 台の接続を 5 本から 3 本に減らすと、1 台の中では問い合わせが順番待ちになります。それでも試験の表示時間は変わりませんでした（どちらも半数が 0.13 秒ほど）。

### 2. 抽選で、景品をまとめてロックしない

もともとは、在庫の残る景品の行をすべて `FOR UPDATE` でロックしてから引いていました。在庫の取り違えは起きませんが、同じ開催回の抽選が 1 件ずつしか進まず、待っている間も接続を握り続けます。

今は「選んだ景品の在庫を、条件付きの UPDATE 1 文で確保する」形にしています。取れなければ、その景品を外して選び直します。

```ts:roulette/draw.ts（抜粋）
const reserved = await prisma.$executeRaw`
  UPDATE "roulette_prize"
  SET "issuedCount" = "issuedCount" + 1, "updatedAt" = now()
  WHERE "id" = ${won.id}::uuid
    AND ("stock" IS NULL OR "issuedCount" < "stock")`
if (reserved === 1) return won
// 同時に最後の 1 本を取られた。この景品を外して選び直す
remaining = remaining.filter((p) => p.id !== won.id)
```

クーポンと参加の記録は、そのあとの短いトランザクションで作ります。そこで失敗したら、確保した在庫を 1 戻します。在庫を確保してから発行するので、出しすぎることはありません。途中で処理が落ちると在庫が 1 本減ったままになりますが、出しすぎる方向には倒れない作りにしました。

### 3. 混雑で落ちたら、少し待ってやり直す

それでも混雑の瞬間は受付上限に当たるので、混雑によるエラーのときだけ、0.3 秒・0.8 秒前後を空けて最大 3 回やり直すようにしました。

```ts:base/db-busy.ts（抜粋）
const BUSY_PATTERNS = [
  /EMAXCONN|max client connections/i,
  /timeout exceeded when trying to connect/i, // pg のプールの空き待ち
  /client_login_timeout/i,
  /Unable to start a transaction in the given time/i, // Prisma の P2028
]
```

抽選は「確定済みなら、その結果を返す」作りなので、やり直しても二重には回りません。待つ時間はわざとばらつかせています。同じ瞬間に落ちた人たちが、同じ瞬間にやり直さないようにするためです。

Prisma のトランザクションの開始待ち（`maxWait`）も、既定の 2 秒から 10 秒に延ばしました。1 台の接続を絞ると順番待ちが増えるので、その待ちだけで開始待ちが切れていたからです。

### 4. 配信を少しずつ送る

試験ではありませんが、そもそも配信を全員に同時に送ると、来訪の山が大きくなります。1,000 人を超える配信は、100 人ずつの組に分けて DB に積み、1 分ごとの cron が 1 分 1,000 人ずつ送る形にしました。

```sql
UPDATE "broadcast_wave" SET "claimedAt" = $now
WHERE "id" IN (
  SELECT "id" FROM "broadcast_wave"
  WHERE "sentAt" IS NULL AND "claimedAt" IS NULL AND "sendAt" <= $horizon
  ORDER BY "sendAt", "seq"
  LIMIT 12
  FOR UPDATE SKIP LOCKED
)
RETURNING *
```

cron が重なっても同じ組を 2 回送らないよう、取るときに `claimedAt` を入れて `SKIP LOCKED` で取っています。取ったまま関数が止まった組は、二重送信を避けるため送り直さずに「失敗」として残します。

### 5. 開くたびの書き込みを減らす

アプリを開くたびに最終ログイン日時とログイン回数を書いていて、これが最大 2 回の UPDATE でした。1 文にまとめ、同じ端末で 30 分以内に開き直した分は送らないようにしています。負荷試験はブラウザの JavaScript を動かさないのでこの書き込みは含まれていませんが、実際の利用では会員の数だけ一斉に来るので、先に減らしました。

## 直したあとの結果

| 条件 | 画面を開く | ルーレットを回す |
| --- | --- | --- |
| 100 人が同じ瞬間に回す | 100% | **100%**（4% から） |
| 1 万人を 10 分に散らす（1 秒に 17 人） | 100% | **100%**（ロックの修正後の 72% から） |
| 1 万人を 5 分に散らす（1 秒に 33 人） | 100% | **100%** |

回す処理は、99% の人が 0.4 秒以内に終わっています。本番の DB は検証環境より大きい規模（Medium、受付上限が約 3 倍）にしているので、さらに余裕があると考えています。ただ、本番では試験していません。

## 万一のときのメンテナンスモード

それでも詰まったときに DB を大きくできるよう、アプリを止めるスイッチも用意しました。Supabase のコンピュートを変えると、DB が 2 分ほど止まるためです。

スイッチは DB ではなく **Vercel の Edge Config** に置いています。DB に置くと、DB が止まっているあいだ読めないからです。デプロイなしで 10 秒ほどで切り替わりました。

```ts
export async function readMaintenance(connectionString: string | undefined) {
  if (!connectionString) return OFF
  try {
    return parseMaintenance(await createClient(connectionString).get("maintenance"))
  } catch {
    return OFF // 読めないときは「通常」に倒す。設定の不具合で全員を締め出さない
  }
}
```

ON の間は、proxy（Next.js 16 の middleware）が DB を使わない静的な HTML を 503 で返します。管理画面から切り替えたくなりますが、管理画面のログインも DB を使うので、DB が止まっているときに戻せなくなります。なので切り替えはスクリプトか、Vercel の管理画面で行う形にしました。

ちなみに、`@vercel/edge-config` は `next dev` のときだけ値を手元に覚えておく作りになっていて、手元では OFF にしてもしばらく ON のままに見えました。ビルドした環境ではこの仕組みは働かず、10 秒ほどで切り替わります。

## 振り返り

今回分かったのは、インスタンスが増えるほど DB への接続も増える、ということでした。Vercel 側がいくら増えても、DB の接続プールの受付上限は増えません。1 台あたりの接続を絞り、混雑したときにやり直せるようにしたのが一番効きました。

あとは、試験の結果を疑うことです。「全員成功」が 404 だったり、手元の PC の限界だったりしたので、成功の判定を厳しくしてから、数字を信じるようにしました。スクリプトは残してあるので、構成を変えたらまた同じ条件で測るつもりです。
