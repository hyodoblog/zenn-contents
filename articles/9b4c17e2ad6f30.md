LINE ミニアプリを開いたとき、ロゴが出るまで白い画面が続き、タブを押しても表示が切り替わるまで時間がかかっていました。

調べると、ルートレイアウト全体を Suspense で囲み、fallback に空の `div` を指定していました。今回は Suspense の範囲を変えた話と、あわせて見直した画像取得やキャッシュについて紹介します。

:::message
本記事は業務システムの開発に伴走した記録です。クライアント名・プロダクト名・業務固有の用語は伏せ、コンポーネント名などは一般的な名前に置き換えています。
:::

## つくっていたもの

飲食店の会員向け LINE ミニアプリです。会員証と予約、店舗一覧、お知らせ。

- **アプリ**: Next.js 16.3（App Router、Cache Components、Partial Prefetching）on Vercel
- **データ**: Supabase（Postgres）+ Prisma
- **認証**: LIFF で LINE ログインし、自前のセッション Cookie を発行
- **併設**: 同じ DB を見る管理画面。別の Next.js アプリとして別ドメインにデプロイ

画面は 11 ルートあり、すべてログインが必要です。

## LIFF を読み込んでいる場所を確認する

LINE ミニアプリは LINE 内の WebView で動きます。起動時に LIFF の初期化とログインのコールバックが挟まるので、まずそこを疑いました。

`liff.init()` が遷移のたびに呼ばれていないか確認したところ、`LiffProvider` を使っているのはログイン画面だけでした。

```bash
grep -rn "LiffProvider" app components lib features
# app/auth/page.tsx:7:    <LiffProvider>
```

ログイン画面の中だけです。ログインが済めば Cookie に切り替わり、残り 10 ルートは LIFF SDK を読み込みません。遷移の遅さには関わっていませんでした。

## Suspense の範囲をタブだけにする

ルートレイアウトはこうなっていました。

```tsx
// app/layout.tsx（変更前）
<body>
  {/* AppShell は usePathname を使うため Suspense 境界が必須 */}
  <Suspense fallback={<div className="app-root min-h-svh" />}>
    <AppShell>{children}</AppShell>
  </Suspense>
</body>
```

コメントの認識は正しいです。`usePathname` や `useSearchParams` はサーバー描画中に中断するため、Cache Components では境界が要ります。公式ドキュメントにも書かれています。

> `useSearchParams()` suspends during server rendering because search params are not available at build time.

今回はタブのハイライトのために URL を読んでいましたが、Suspense の範囲がアプリ全体になっていました。fallback も空なので、待っている間は何も表示されません。

境界をタブだけに縮めます。

```tsx
// components/app-shell.tsx（変更後）
<main id="main-content" className="relative flex-1 min-w-0">{children}</main>
{/* URL を読むのはタブだけ。解決前もタブの枠は出す */}
<Suspense fallback={<Tabs />}>
  <ActiveTabs />
</Suspense>
```

fallback を空にせず、ハイライトなしのタブを出すのがポイントです。URL が分かる前でも、タブは同じ位置に同じ形で並びます。

同じ調査で、ほかに 2 か所も見直しました。ひとつは自前のプログレスバーで、`usePathname` と `useSearchParams` を購読する 96 行のクライアントコンポーネントです。Next.js の `useLinkStatus` に置き換えて 24 行になりました。

もうひとつはタブに付けていた `prefetch` の強制指定です。Partial Prefetching は**ルートごとに 1 枚の再利用できるシェル**を取りに行くので、全リンクに `prefetch` を付けると利点を自分で打ち消します。外しました。

確認した箇所と対応をまとめます。

| # | 確認したこと | 結果 |
| --- | --- | --- |
| 1 | `liff.init()` が毎回走っている | ログイン画面だけで初期化していた |
| 2 | DB が遅い | 今回、最初に見直したのは描画を待つ範囲 |
| 3 | ルートレイアウトの `<Suspense>` | 空の fallback で全画面を待たせていたため、範囲を変更 |
| 4 | 自前プログレスバーの URL 購読 | `useLinkStatus` へ変更 |
| 5 | 全リンクへの `prefetch` 強制 | 強制指定を外した |

## 画像だけが、ログイン画面へ飛ばされていた

全ルートがログイン必須なので、プロキシで未認証を弾いています。除外設定はこうでした。

```ts
matcher: [{ source: "/((?!_next/static|_next/image|favicon.ico|api/).*)" }]
```

`_next/image` を除外しているので安心していました。**除外すべきだったのは、元画像のパスのほうです。**

画像最適化は、リクエストを受けたあとサーバーが自分でオリジンへ取りに行きます。この内部リクエストに会員の Cookie は付きません。つまり `/brand/hero.jpg` が未認証と判定され、ログイン画面へリダイレクトされていました。

```ts
// next/image のサーバー側取得には会員Cookieが付かない。公開画像を認証しない。
matcher: [{ source: "/((?!_next/static|_next/image|favicon.ico|brand/|api/).*)" }]
```

再発しないよう、`unstable_doesMiddlewareMatch` で境界をテストに固定しています。公開画像を取得するときに、認証画面へリダイレクトされないことも確認しています。

## 会員データは画面で使う分だけ取得する

全ルートがログイン必須ということは、中身のほとんどが会員ごとに違うということです。共有キャッシュに載せられるのは、店舗一覧やお知らせのような公開カタログだけでした。

```bash
grep -rn '"use cache"' features app | wc -l
# => 7
```

会員データについては、まず取得する量を見直しました。

ところが会員取得は `getMember()` の 1 本に集約され、どの画面もこれを呼んでいました。中身は会員検索とマイレージ集計、そして予約 20 件です。予約履歴を出すのはマイページだけなのに、他の画面も 20 件を取っていました。

3 段に割り、画面ごとに呼び分けます。

```ts
/** 認証と会員の解決はリクエスト内で共有。個人情報を共有キャッシュへ入れない。 */
export const getMemberIdentity = cache(async () => { /* 会員検索のみ */ })

/** ホーム・ランク判定用。予約履歴は取得しない。 */
export const getMemberSummary = cache(async () => { /* + マイレージ集計 */ })
```

| 画面 | 変更前 | 変更後 |
| --- | --- | --- |
| ホーム・予約・裏メニュー | 会員検索 + 集計 + 予約 20 件 | 会員検索 + 集計 |
| 会員証の引き換え | 会員検索 + 集計 + 予約 20 件 | 会員検索のみ |
| マイページ | 会員検索 + 集計 + 予約 20 件 | 同じ内容。集計と予約は並列 |

React の `cache()` はリクエストの中だけで共有します。複数の `<Suspense>` 境界から呼んでも DB へは 1 回、かつリクエストをまたいで残りません。個人情報の置き場として都合がよいです。

店舗詳細も直しました。スラッグごとに `use cache` を付けて個別に引いていたのを、一覧のキャッシュから拾う形にしています。

```ts
/** 一覧と詳細で同じ店舗キャッシュを再利用する。 */
export async function getStoreBySlug(slug: string): Promise<Store | null> {
  return (await listStores()).find((store) => store.id === slug) ?? null
}
```

## 管理画面からの失効。updateTag は使えなかった

公開カタログをキャッシュに載せると、次は「管理画面で直したとき、いつ新しくなるか」が問題になります。

以前の記事では、Server Action から `updateTag` を使いました。今回は同じ方法を使えません。管理画面が別デプロイなので、失効は外から叩かれる Route Handler に届くからです。公式ドキュメントは、Server Action の外から失効させる場合をこう書いています。

> `updateTag` is not available. Pass `{ expire: 0 }` to expire the data immediately.

```ts
// Route Handler では updateTag は使用不可。次回の取得で最新値を待つ。
revalidateTag(CATALOG_TAG[key], { expire: 0 })
```

受け口は Bearer の固定長比較、本文 1 KB まで、タグは 7 種類の許可リストだけにしました。送る側は保存を返してから `after()` で通知し、1.5 秒でタイムアウトします。**保存は成功しているのに、通知の失敗で画面にエラーを出すほうが害が大きい**からです。届かなくても、時間切れで最後は新しくなります。

## ドキュメントに書いてあること、書いていないこと

キャッシュ寿命はプロファイル名をやめ、`cacheLife({ stale: 300, revalidate: 300, expire: 600 })` のように秒で書きました。このとき社内メモに「5 分以上にすると App Shell に公開データを含められる」と書いています。

公式ドキュメントを読み直したら、5 分が出てくるのは別の文脈でした。

> ... as long as its `stale` time is at least 5 minutes.

これは `use cache: private`、つまり Cookie などを読むプライベートなキャッシュの条件です。公開データの `use cache` に同じ下限がある記述は見つけられませんでした。5 分は条件ではなく、私たちが選んだ値です。今回は選んだ設定値として扱い、App Shell に含めるための必須条件とは書かないようにします。

## 数えたもの、測っていないもの

ミリ秒の前後比較はありません。数えたものだけです。

- ルートレイアウトの `<Suspense>`: 全画面を包む 1 個 → タブだけを包む 1 個
- 自前プログレスバー: 96 行 → `useLinkStatus` で 24 行
- `use cache`: 7 箇所。すべて公開カタログ
- 会員まわりの取得: 引き換え画面は 3 本から 1 本、ホームは 3 本から 2 本
- 実行リージョン: 米国東部の既定値から東京へ

改善率は測っていません。代わりに、崩れたら気づけるようにしました。`instant()` ヘルパーで「クリック直後に何が見えているか」をテストに固定しています。境界を上へ動かすと、ここが落ちます。

```ts
await instant(page, async () => {
  await page.click('a[href="/mypage"]')
  await page.waitForURL((url) => url.pathname === "/mypage")
  await expect(page.getByRole("heading", { name: "会員証" })).toBeVisible()
})
```


## おわりに

今回は、タブが URL を待つ間にも画面の枠を表示できるよう、Suspense の範囲と fallback を変えました。LIFF の初期化を調べていましたが、Next.js 側のレイアウトも確認する必要がありました。

この変更では表示時間の前後比較は取れていません。測定した改善率として紹介することはできませんが、同じような構成を確認するときの参考になればと思います。
