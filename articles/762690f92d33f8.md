前の記事で、社内向けのサイトを Basic 認証で閉じました。10 分で終わって、私はしばらくそれで足りると思っていました。足りないと分かったのは、そのあと自社の別の業務システムを開いたときです。同じことを Basic 認証でやろうとすると、まったく届きませんでした。

そちらでは Better Auth の organization プラグインを使っています。結論から言うと、招待制とロールは素直に載ります。一方で **organization プラグインの標準 API は、組織に所属してさえいれば他のメンバーのロールを引けます**。仕様どおりの挙動ですが、社内アプリの要件がそれより厳しいなら、自分で絞ることになります。

同じように Basic 認証から先へ進もうとしている人の時短になれば嬉しいです。前回の記事の続きにあたるので、まだの方はこちらからどうぞ。

https://zenn.dev/yoshinani_dev/articles/3306277f57fd1c

:::message
社内および受託で運用している業務システムの実装をもとにしています。クライアント名・プロダクト名・業務固有の用語は伏せ、組織名やロール名は一般的な名前に置き換えています。ライブラリの挙動は better-auth 1.6.23 の実装を読んで確認した内容です。
:::

## Basic 認証で足りなくなったところ

Basic 認証は、外から読めない状態を作るところまでは仕事をします。そこから先が弱いです。

| 欲しくなったこと | Basic 認証だと |
| --- | --- |
| 誰が見たか記録したい | 全員が同じ資格情報なので分からない |
| 退職者を外したい | パスワードを変えて全員へ配り直す |
| 閲覧だけの人を作りたい | 分けられない |
| 管理者だけの画面を作りたい | 分けられない |

> 退職者が出たらパスワードを変えればいい話だと思っていました。

済みませんでした。変えた瞬間、残る全員へ配り直しになります。配り直した先で誰かが古いほうを使い続けても、こちらからは分かりません。

**Basic 認証は「入口を閉める」ためのもので、「誰が何をしてよいか」を扱う道具ではありません。** 社内アプリでも、人が増えて役割が分かれた時点で足りなくなります。

## つくったもの

- **アプリ**: Next.js（App Router）のモノレポ
- **認証**: Better Auth 1.6.23 + organization プラグイン
- **データ**: Postgres + Prisma（`prismaAdapter`）
- **メール**: Resend（招待メール）
- **運用**: 組織は 1 つに固定し、管理者が招待して増やす

ロールは 3 つだけにしました。管理者・編集者・閲覧者です。

```ts:organization-auth-roles.ts
import { defaultAc } from "better-auth/plugins/organization/access"

// 管理者だけが、招待とメンバー操作を持つ
const adminRole = defaultAc.newRole({
  organization: ["update"],
  member: ["create", "update", "delete"],
  invitation: ["create", "cancel"],
  team: [],
  ac: ["read"],
})

// 編集者と閲覧者は、組織まわりの権限を一切持たない
const editorRole = defaultAc.newRole({ organization: [], member: [], invitation: [], team: [], ac: ["read"] })
const viewerRole = defaultAc.newRole({ organization: [], member: [], invitation: [], team: [], ac: ["read"] })

export const organizationAuthRoles = {
  admin: adminRole,
  editor: editorRole,
  viewer: viewerRole,
}
```

編集者と閲覧者は、この定義だと同じ中身です。差は業務データ側で付けています。**organization プラグインのロールは、業務の権限ではなく組織まわりの操作を縛るためのもの**だと割り切ったほうが、あとで混乱しません。

## 招待制にする：組織を 1 つに固定する

社内アプリなので、ユーザーが組織を作れる必要はありません。むしろ作れると事故ります。プラグイン側で閉じられます。

```ts:auth.ts
organization({
  // 組織はシードで用意した 1 つだけを使う運用のため、
  // ユーザーによる新規作成と削除を禁止して固定する
  allowUserToCreateOrganization: false,
  disableOrganizationDeletion: true,
  // creatorRole を管理者にすることで、最後の管理者の降格・削除も
  // Better Auth 側で拒否される
  creatorRole: "admin",
  roles: organizationAuthRoles,
  requireEmailVerificationOnInvitation: false,
  async sendInvitationEmail(data) {
    // 招待リンクを組み立ててメールで送る
  },
})
```

`creatorRole: "admin"` にしておくと、**最後の管理者を降格・削除しようとしたときにライブラリ側が拒否します**。管理者が 0 人になって誰も招待できない状態は、自前で書くと落としやすい分岐です。ここを任せられるのは楽でした。

サインアップは開けていません。入口は招待だけです。メール認証も、社内利用に限るので飛ばしています。

```ts:auth.ts
databaseHooks: {
  user: {
    create: {
      before: async (user) => ({
        // 社内利用のためメールアドレスの認証をスキップ
        data: { ...user, emailVerified: true },
      }),
    },
  },
},
```

外部の人が登録しうるサービスでこれをやると穴になります。**招待制であることと、この設定は必ずセットです。**

## proxy は防御線にしない

Next.js の `proxy.ts`（旧 `middleware.ts`）でセッションを見て弾きたくなります。実際に書いていますが、役割は限定しています。

```ts:proxy.ts
import { getSessionCookie } from "better-auth/cookies"
import { type NextRequest, NextResponse, type ProxyConfig } from "next/server"

/**
 * 未ログインをサインインへ送る楽観的な判定
 *
 * getSessionCookie はクッキーの有無を見るだけで、署名の検証も所属の確認もしない。
 * ここは「体感を速くするための前捌き」であって防御線ではない。
 */
export function proxy(request: NextRequest) {
  const sessionCookie = getSessionCookie(request)

  if (!sessionCookie) {
    const url = new URL("/auth/sign-in", request.url)
    url.searchParams.set("redirectTo", request.nextUrl.pathname)
    return NextResponse.redirect(url)
  }

  return NextResponse.next()
}

export const config: ProxyConfig = {
  matcher: [
    { source: "/((?!_next/static|_next/image|favicon.ico|api/|auth/).*)" },
  ],
}
```

`getSessionCookie` は**クッキーがあるかどうかしか見ません**。署名の検証も、組織に所属しているかの確認もしません。偽のクッキーを付ければ通過します。通過した先で落とす前提の作りです。

前回の記事で「`matcher` の除外に `api` を入れると、API が認証の外に出る」と書きました。ここでは意図して `api/` を外しています。**防御線を下の層へ置いたからです。** proxy を防御線にするなら `api` を外してはいけませんし、防御線を下に置くなら外してかまいません。危険なのは、置き場所を決めないまま定型の除外パターンを貼ることです。

Next.js の公式も、Server Functions を proxy 頼りにせず処理の中で確認するよう書いています。実際の認可は、こちらに集めました。

```ts:organization-guard.ts
import "server-only"
import { headers } from "next/headers"
import { cache } from "react"

import { auth } from "@repo/schema/src/auth"

/** セッションの検証。クッキーの有無ではなく better-auth に実体を確かめさせる */
const getVerifiedSession = cache(async () =>
  auth.api.getSession({ headers: await headers() }),
)

export const requireOrganization = async (slug: string) => {
  const session = await getVerifiedSession()
  if (!session) return unauthorized()

  const membership = await getMembership(session.user.id, slug)
  if (!membership) return forbidden({ slug })

  return membership
}
```

`cache()` で包んでいるのは、1 リクエスト内の重複を潰すためです。レイアウトとページと複数のコンテナが同じガードを呼んでも、セッションと所属はそれぞれ 1 回しか引きません。

### ID は引数で来る。所属だけでは足りない

Server Action は URL を経由せず、引数で ID を受け取ります。ここが画面と違うところです。

所属を確認しただけだと、**他組織のリソース ID を引数に渡された場合を弾けません**。そこで、リソースがその組織のものかまで確かめています。

```ts:organization-guard.ts
const requireResource = async (
  slug: string,
  resourceId: string,
  belongsToOrganization: (orgId: string, resourceId: string) => Promise<boolean>,
) => {
  const membership = await requireOrganization(slug)
  if (membership instanceof TaggedError) return membership

  const belongs = await belongsToOrganization(
    membership.organizationId,
    resourceId,
  )
  if (!belongs) return forbidden({ slug, resourceId })

  return membership
}
```

画面側では、他組織のリソースを 403 ではなく **404 として返しています**。403 だと「その ID は存在する」と教えてしまうためです。

## 標準 API は、メンバーなら他人のロールも引ける

ここが一番の発見でした。organization プラグインは、ブラウザーから叩ける API を一式生やします。その中の `get-active-member-role` は、`userId` を渡せます。

> 自分のロールを取る API に、他人の ID を渡せる理由が分かりません。

ドキュメントを読んでも、誰が呼べるのかは書いていませんでした。書いていないなら実装に書いてあります。`node_modules` を開きました（better-auth 1.6.23）。

```js:crud-members.mjs
const isMember = await adapter.findMemberByOrgId({
  userId: session.user.id,
  organizationId
})
if (!isMember) throw APIError.from("FORBIDDEN", ...)

if (!ctx.query?.userId) return ctx.json({ role: isMember.role })

const userIdToGetRole = ctx.query?.userId
const member = await adapter.findMemberByOrgId({
  userId: userIdToGetRole,
  organizationId
})
return ctx.json({ role: member?.role })
```

確認しているのは「**呼んだ人がその組織のメンバーかどうか**」だけです。メンバーでありさえすれば、`userId` に他人を指定してロールが返ってきます。管理者かどうかは見ていません。

すぐ上にある `listMembers` も同じ考え方で、メンバーなら組織のメンバー一覧を並べられます。並び替えも絞り込みもできます。閲覧者に渡したアカウントから、誰が管理者かを 1 リクエストで数えられる、ということです。

**これは脆弱性ではありません。** クエリパラメータには「指定しなければ現在のユーザーになる」という説明が付いていて、意図された仕様です。organization プラグインの前提は「組織のメンバーは組織の情報を読める」で、多くの SaaS ではそれで正しいです。

問題は、社内アプリの要件がそこより厳しいときです。閲覧者に他の人の権限を見せたくない、メンバー一覧は管理者だけ、という要件は普通にあります。そこで、ブラウザーへ公開するエンドポイントを allowlist にしました。

```ts:organization-auth-route-policy.ts
const CLIENT_ORGANIZATION_ENDPOINTS = new Set([
  "GET /organization/get-active-member",
  "GET /organization/get-active-member-role",
  "GET /organization/get-invitation",
  "GET /organization/list",
  "GET /organization/list-user-invitations",
  "POST /organization/accept-invitation",
  "POST /organization/has-permission",
  "POST /organization/reject-invitation",
  "POST /organization/set-active",
])
```

本人向けの操作 9 つだけを通し、それ以外は既定で拒否します。ユーザー管理は、管理者ガードを通した独自の Server Action へ集約しました。`get-active-member-role` は許可していますが、`userId` が付いていたら拒否します。

```ts:organization-auth-route-policy.ts
// 本人のロール取得だけを許可する。userId を指定できる標準 API は、所属して
// さえいれば別メンバーのロールを照会できるため公開しない。
if (
  endpoint === "/organization/get-active-member-role" &&
  url.searchParams.has("userId")
) {
  return { allowed: false, reason: "other-user-role" }
}
```

判定は Route Handler で挟みます。

```ts:app/api/auth/[...all]/route.ts
const handlers = toNextJsHandler(auth.handler)

export function GET(request: Request) {
  const decision = decideOrganizationAuthRoute(request)
  return decision.allowed ? handlers.GET(request) : forbidden()
}
```

**allowlist にした理由は、将来増えるエンドポイントを既定で拒否したいからです。** 拒否リストにすると、ライブラリを上げたときに増えた API が黙って通ります。

なお、パスの判定ではパーセントエンコードを 2 回まで正規化しています。エンコードで allowlist を迂回されないためです。Next.js と Better Auth のどちらが先にデコードしても、同じ結論になるようにしています。

## セッションの検証を、毎回 DB に聞かない

画面も Server Action も毎回セッションを検証します。素直に書くとリクエストごとに DB への問い合わせが増えます。Better Auth にはクッキーへ短時間だけ写す仕組みがあります。

```ts:auth.ts
session: {
  cookieCache: {
    enabled: true,
    maxAge: 5 * 60,
  },
},
```

ここで気を付けるのは、**何が遅れて何が遅れないか**です。

- **組織からの除名は即座に効く**。所属は毎回 DB から引いているため
- **遅れるのはセッション自体を無効化したときだけ**。最大で `maxAge` 秒

退職者を外す操作が 5 分遅れるのかどうかは、社内アプリだと直接効いてくる論点です。所属の確認を DB に残しておけば、ここは遅れません。

## 事故りやすいところ

### 環境変数が無いまま起動しない

招待リンクの土台になる URL が未設定だと、`undefined/auth/...` という開けない URL をメールで配ります。届いてから気付くやつです。起動時に落としました。

```ts:auth.ts
const appUrl = process.env.APP_URL

if (!appUrl) {
  throw new Error("APP_URL is not set")
}
```

前の記事にも書いた話の繰り返しですが、**設定漏れは開く側ではなく閉じる側に倒します**。

### メール送信の失敗が握り潰される

Resend の SDK は、HTTP エラーでも例外を投げずに `{ error }` を返します。戻り値を捨てると、送信元ドメインの未認証や API キーの失効に誰も気付けません。招待が届かないという問い合わせが来て、初めて分かります。

```ts:auth.ts
const { error } = await resend.emails.send({ /* ... */ })

if (error) {
  const reason = `${error.name}: ${error.message}`
  saveInvitationEmailFailure(data.id, reason)
  throw new Error(`招待メールの送信に失敗した (${reason})`)
}
```

Better Auth はこの例外を握り潰してログに出すだけですが、DB へ理由を残しておけば後から追えます。

### 生成 URL を trustedOrigins に入れる

プレビュー環境から認証を試すために、Vercel の生成 URL をワイルドカードで許可しています。

```ts:auth.ts
trustedOrigins: [
  process.env.BETTER_AUTH_URL!,
  "https://*-acme.vercel.app",
],
```

前の記事で書いたとおり、Vercel の生成 URL は推測できる形をしています。**ここを広げるほど、認証を試せる場所が増えます。** プレビューに Deployment Protection がかかっている前提で許可しました。かかっていないなら、絞るべきところです。

## チェックリスト

認可まわりで決めることを、項目へ落としました。公開範囲や秘密情報まで含む全 66 項目は、[GitHub の詳細版](https://github.com/hyodoblog/zenn-contents/blob/main/docs/internal-app-checklist/checklist.md)にあります。

- [ ] 組織の新規作成と削除を止めた
- [ ] `creatorRole` を管理者にして、最後の管理者が消えない状態にした
- [ ] サインアップを閉じ、入口を招待だけにした
- [ ] メール認証を飛ばす判断が、招待制であることとセットになっている
- [ ] proxy を防御線にしているのか、前捌きなのかを決めた
- [ ] 前捌きなら、画面・Server Action・Route Handler のそれぞれにガードを置いた
- [ ] Server Action で、引数の ID がその組織のものか確かめている
- [ ] 他組織のリソースを 403 ではなく 404 にして、存在を伏せた
- [ ] ブラウザーへ公開するエンドポイントを許可リストにした
- [ ] `get-active-member-role` に `userId` を付けた呼び出しを塞いだ
- [ ] `cookieCache` の分だけ、何の反映が遅れるか把握した
- [ ] 招待メールの送信失敗が、ログではなく追える場所に残る

## 学び

### 1. Basic 認証とロールは、別の問題を解いている

Basic 認証は入口を閉めます。ロールは、入った人の権限を分けます。**入口を閉めた安心感で、権限の設計を先送りにしていました。** 人が 3 人を超えたあたりで、必ず必要になります。

### 2. ライブラリの前提と、自分の要件を突き合わせる

organization プラグインの前提は「メンバーは組織の情報を読める」です。SaaS では正しく、社内アプリでは緩すぎることがあります。**仕様どおりに動いているものを、自分の要件に合っているとは限らないものとして読む**。この一手間を飛ばすと、標準 API がそのまま穴になります。

### 3. 塞ぐなら拒否リストではなく許可リスト

拒否リストは、ライブラリを上げたときに増えた API を黙って通します。許可リストなら既定で止まります。**バージョンアップで穴が開く側と、バージョンアップで壊れて気付く側なら、後者を選びます。**

### 4. 防御線の場所を先に決める

proxy に置くのか、その下に置くのか。決めてから `matcher` を書けば、除外パターンは判断の結果になります。決めずに定型を貼ると、除外パターンが判断そのものになってしまいます。**先に決めるのは実装ではなく、どこで守るかです。**

## おわりに

Basic 認証から Better Auth へ移して増えたのは、コードの量よりも決めることの量でした。誰が招待できるか、何人まで管理者を許すか、退職者を外したとき何秒で効いてほしいか。ライブラリはこれらを聞いてはくれますが、決めてはくれません。

そして、標準 API が何を許しているかは、ドキュメントよりも実装を読んだほうが速いことがありました。`node_modules` の中を開くのは面倒ですが、今回いちばん確かな情報源はそこでした。
