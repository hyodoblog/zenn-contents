朝、クライアントから「Bot がオフラインです」と連絡が来ました。Cloud Run のコンソールを開くと、サービスは `Ready`。ヘルスチェックはこう返ってきます。

```json
{"status":"down","checks":{"db":"ok"},"discord":{"connected":false,"status":"disconnected"}}
```

結論から言うと、犯人は Discord 側の障害ではなく、**その失敗を catch して「HTTP サーバーだけは生かしておく」と書いた自分たちのコード**でした。Discord は 1 時間で復旧していましたが、私たちの Bot は 39 時間つながらないまま生きていました。

同じように常駐接続のプロセスを運用している人の時短になれば嬉しいです。

:::message
本記事は業務システムの開発に伴走した記録です。クライアント名・プロダクト名・本番のホスト名は伏せています。
:::

## つくっていたもの

チャットツール上で動く業務用の Bot です。届いたメッセージを保存して、設定に応じて AI が返信します。

- **Bot 本体**: Node.js + discord.js v14。Cloud Run で常駐（`min-instances: 1`）
- **管理画面**: Next.js on Vercel

同じ機能を LINE や Slack にも出しているのですが、Discord だけ仕組みが違います。他は Webhook なのでリクエストが来たときだけ動く。Discord は Gateway という WebSocket を張りっぱなしにします。

**つながっていること自体が機能**。ここが落とし穴でした。

## Discord は 50 分で直っていた

ログを見ると、切断のきっかけはすぐ出てきました。

```
[ERROR] Discord shard error: Error: Unexpected server response: 503
```

Discord Status にも同じ時刻にインシデントが立っています。

> 外部要因か。Discord が直れば、こちらも勝手に戻るはず。

戻りませんでした。向こうは 50 分で `resolved` になっています。その後の 38 時間、こちらのログには何も出ていません。エラーすら出ない。

コードを読み直すと、切断時は `process.exit(1)` して基盤に再起動させる設計になっています。実際、ログでも 2 回は再起動していました。そして 3 回目の起動を最後に、ログが途切れます。

## 最後のエラーだけ、WebSocket ではなかった

```
[ERROR] Failed to start Discord Gateway service: HTTPError: Internal Server Error
    at async WebSocketManager.fetchGatewayInformation (@discordjs/ws)
    at async Client.login (discord.js/src/client/Client.js)
  status: 500,
  method: 'GET',
  url: 'https://discord.com/api/v10/gateway/bot'
```

WebSocket が切れたのではありません。`login()` が、その手前の REST で 500 を食らっています。

discord.js の `login()` は、WebSocket をつなぐ前に `GET /gateway/bot` で接続先を取りに行きます。ここで落ちると WebSocket は一度も張られない。張られていないので `shardError` も `shardDisconnect` も発火しません。

つまり、私たちが用意した「イベントを受けて再起動する」経路には、一生入りません。

では例外はどこへ行ったのか。呼び出し元です。

```typescript
discordGatewayService.start().catch((error) => {
  logger.error("Failed to start Discord gateway service:", error)
  // Don't exit immediately - keep HTTP server running for health checks
})
```

これでした。

ヘルスチェックに応答できるよう HTTP サーバーを生かしておく。書いた当時の判断も理解できます。起動に失敗するたびクラッシュループするより、状態を見られるほうがいい。

ただしこのコードは、繋がらないまま生き続けるプロセスを全力で維持します。しかも再試行しません。永遠に。

## `/health` は誰にも読まれていなかった

`/health` は正しく 503 を返していました。アプリは自分が壊れていることを知っていたわけです。それでも 39 時間、誰にも伝わりませんでした。

プローブの設定を見にいきます。

```bash
gcloud run services describe discord-bot --region asia-northeast1 \
  --format="yaml(spec.template.spec.containers[].livenessProbe,spec.template.spec.containers[].startupProbe)"
```

```yaml
startupProbe:
  tcpSocket:
    port: 8080
```

`tcpSocket` の startupProbe だけ。`livenessProbe` はありません。

startupProbe は起動時にしか走らず、しかも TCP なので 8080 が開いていれば合格です。HTTP サーバーは生きているので当然通ります。一度通れば、あとは何時間 503 を返しても Cloud Run は何も言いません。

`/health` は、誰にも読まれない日記でした。

## 直したこと

方針は 1 つ、**繋がらないまま生き続けさせない**ことです。1 つの仕組みに賭けると、今回のように「そのイベントが発火しない経路」で抜けられるので、何段か重ねました。

まず `login()` を指数バックオフで再試行して、諦めたら自分で終了します。

```typescript
try {
  await client.login(env.DISCORD_BOT_TOKEN)
  return
} catch (error) {
  if (attempt >= LOGIN_MAX_ATTEMPTS) {
    // 例外を投げて呼び出し元に任せない。また誰かが親切に catch する
    this.exitForRestart("Discord login failed")
    return
  }
  await this.wait(backoffMs(attempt))
}
```

切断のほうは、すぐ落とさず 60 秒の猶予を置きました。discord.js は自前で再接続するので、瞬断のたびに殺すと直るものまで巻き込みます。猶予が切れた時点で `isReady()` を見て、戻っていなければ終了します。判断の基準を「イベントが来たか」ではなく「実際に繋がっているか」にしたのが肝でした。

加えて 30 秒間隔のウォッチドッグで `isReady()` を確認しています。今回いちばん怖かったのは、イベントが 1 つも発火しないまま死ぬ経路があったことです。イベント駆動の復帰処理は、イベントが来ない故障に無力でした。

最後に liveness probe です。

```bash
gcloud run services update discord-bot --region asia-northeast1 \
  --liveness-probe "httpGet.path=/health,httpGet.port=8080,periodSeconds=30,failureThreshold=3"
```

90 秒連続で 503 なら Cloud Run が作り直します。**これはコードの再デプロイなしで入れられる**ので、障害対応の当日、ビルドを待たずに先に効かせられました。

そのうえで、10 分間隔で `/health` を叩いて異常なら Discord の Webhook へ通知する cron を足しました。Webhook は Gateway と無関係な REST なので、Bot が落ちていても通知だけは飛びます。

## 消えた 39 時間分のメッセージ

Bot が戻れば終わり、ではありませんでした。止まっていた間に届いたメッセージは DB にありません。Gateway のイベントは再送されないからです。

Discord には REST で履歴を取る API があるので、期間を指定して埋めるスクリプトを書きました。保存キーをメッセージ ID にして冪等にし、通常の受信経路を通さないようにしています。通してしまうと、2 日前のメッセージに AI が今さら返信します。

踏んだのは、既存の履歴同期コードのこれです。

```typescript
// 過去のメッセージを保存したのに、現在時刻を入れてしまう
await updateChannel({ id: channelId, lastMessageAt: new Date() })
```

過去を埋める用途で走らせると、「最終発言は今」という嘘が全チャネルに書かれます。返信漏れの検知や一覧の並び順が、復旧作業のせいで壊れる。保存したメッセージの最大時刻を入れ、既存値より新しいときだけ更新するよう直しました。

最終的に 972 件を戻しています。

## おわりに

39 時間を作ったのは、高度な技術的問題ではありません。`catch` に書いた 1 行のコメントと、`livenessProbe` を設定しなかったこと。どちらも実装した日には合理的に見えました。

書いたときは良いことをしたつもりでした。実際には、壊れたプロセスの延命装置です。外部接続に失敗したまま生き続ける選択肢は、そもそも用意してはいけませんでした。

`/health` の実装自体は満点だったと思います。それでも誰も読んでいなければ、ただの日記です。エンドポイントを作った時点では、監視は 1 ミリも実装されていません。

Discord 側の障害は 50 分、こちらの損害は 39 時間分の会話でした。差の 38 時間は外部要因ではなく、設計の結果です。落ちたこと自体より、落ちたまま気づかない時間のほうが高くつきました。

常駐接続を持つプロセスを書くときは、**繋がらないときに何分後に死ぬか**を先に決めておくといいです。答えが「死にません」なら、今回と同じ設計です。
