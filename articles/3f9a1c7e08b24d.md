Next.js と Supabase で作った管理画面の表示が遅く、同じチームの別の管理画面と構成を比較しました。

調べると、データの取得経路や DB への往復回数が違っていました。Vercel と Supabase のリージョンも離れていたため、接続先とキャッシュを見直しています。今回は、その調査と変更内容を紹介します。

:::message
本記事は業務システムの開発に伴走した記録です。クライアント名・プロダクト名・業務固有の用語は伏せ、テーブル名などは一般的な名前に置き換えています。
:::

## つくっていたもの

社内向けのバックオフィスです。商品マスタを管理して、原価を入力して、帳票を出す。日常的に使う画面です。

技術構成はこんな感じです。

- **アプリ**: Next.js 16（App Router）on Vercel。React Server Components で描画
- **データ**: Supabase（Postgres）+ Prisma 7（Driver Adapters）
- **認可**: Better Auth + アプリ層のガード。全 Server Action で再検証

比較対象になったのは、同じチームが持っている別プロダクトの管理画面です。こちらは全ページ `'use client'` で、ブラウザから PostgREST を直接叩いています。

## 別の管理画面と比較する

別の管理画面が速いと聞いて触ってみると、画面の枠が先に表示され、その後すぐに表が埋まりました。自分たちの画面では、遷移のたびに待ち時間があります。

まずクエリやインデックスを確認しましたが、対象は数千行のテーブルで、調べたクエリは数ミリ秒でした。そこで、速いほうがどのようにデータを取得しているかを確認しました。

```tsx
export default function AdminUsers() {
  const [users, setUsers] = useState<Profile[]>([])

  useEffect(() => {
    void (async () => {
      const { data } = await supabase
        .from("profiles")
        .select("*")
        .order("created_at", { ascending: false })
        .limit(200)
      setUsers((data ?? []) as Profile[])
    })()
  }, [])
  // ...
}
```

この画面では、キャッシュや `Suspense` を使わずにデータを取得していました。ページの HTML はビルド時に確定して CDN から出ます。遷移はクライアントルーティングだけで完結し、サーバー関数を一度も通りません。骨組みが即座に出て、そのあとブラウザから東京の Supabase へ 1 往復。認可は RLS が持つので、anon key をブラウザに置けます。

| | 隣の画面 | うちの画面 |
| --- | --- | --- |
| 画面の実体 | 全ページ `'use client'` | 全ページ Server Components |
| データ経路 | ブラウザ → PostgREST 直 | ブラウザ → 関数 → Prisma → Postgres |
| 認可 | RLS（DB 側） | アプリ層のガード |
| 遷移時のサーバー往復 | 0 回 | 毎回 1 回とその先の DB 往復 |

同じ Supabase を見ていても、**間に挟まっているものの数**が違いました。

## Suspense の確認で見落としたこと

「ストリーミングが足りていないのでは」と考えて、こう数えました。

```bash
for f in $(find app -name "page.tsx"); do
  echo "$(grep -c '<Suspense' $f) $f"
done
```

30 ページ中、`<Suspense>` を含むのは 6 ページ。

この結果から Suspense が足りないと考えましたが、見落としがありました。このリポジトリには `loading.tsx` が全ルートに置かれていて、Suspense 境界はとっくに全ページに存在していたのです。`loading.tsx` は該当セグメントを自動で Suspense に包むので、`page.tsx` を grep しても当然ヒットしません。

`page.tsx` だけの検索では、実際の Suspense 境界を数えられていませんでした。

## DB への往復回数とリージョンを確認する

数え直したのは、Suspense の数ではなく **画面 1 枚あたりの DB 往復**でした。一覧画面はこうなっていました。

1. 所属の確認（1 本）
2. 件数・種別の候補・取引先の候補（3 本を並列）
3. 一覧本体（1 本）

**クエリ 5 本、直列 3 往復。**

ここに、もうひとつの事実が重なります。`vercel.json` が無く、`preferredRegion` の指定もありませんでした。つまり Vercel の既定である `iad1`、米国東部です。

Supabase は東京にありました。サーバーから DB を呼ぶたびに、米国東部と東京の間を往復していたことになります。

クエリの実行時間に加えて、この通信時間もかかります。そこで、リージョンを合わせることと、直列に待っている処理を減らすことの両方を進めました。

## 打った手

### 1. リージョンを DB に寄せる

Vercel のダッシュボードで Settings → Functions → Function Region を東京（`hnd1`）に変更しました。この設定は新しいデプロイから効くので、変更後にリデプロイが要ります。

効いたかどうかは、推測せずに確かめられます。ビルド成果物のリージョンは CLI で見えます。

```bash
vercel inspect https://your-app.vercel.app
```

```
├── λ index (4.82MB) [hnd1]
├── λ _global-error (4.82MB) [hnd1]
```

実際にリクエストを処理したリージョンは、レスポンスヘッダに出ます。

```bash
curl -sS -o /dev/null -D - https://your-app.vercel.app/ | grep -i x-vercel-id
```

```
x-vercel-id: hnd1::srl6v-1788069589640-4b3dc499a33a
```

`hnd1` が返ってきたときは、素直に嬉しかったです。

### 2. 往復を 3 回から 2 回へ

5 本のクエリから 2 本削れました。

ひとつ目は、絞り込みプルダウンの候補です。検索語やページ番号で中身が変わりません。変わるのはマスタを書き換えたときだけです。一覧のクエリから切り離しました。

ふたつ目は、件数と本体です。互いに独立して引けるのに直列でした。並列にできない理由はページ番号の丸めで、`skip` を決めるのに総件数が要ります。

そこで、URL の値をそのまま使って先に投げ、範囲外だったときだけ引き直す形にしました。

```ts
const pageSize = resolvePageSize(query)
const requestedPage = Math.max(Math.trunc(query.page ?? 1), 1)

// 件数と本体は互いに独立して引けるので、往復を重ねずに並べて投げる
const [totalCount, requestedRowList] = await Promise.all([
  client.productMaster.count({ where }),
  findRowList(where, orderBy, requestedPage, pageSize),
])

const pagination = resolvePagination(totalCount, query)
const rowList =
  pagination.page === requestedPage
    ? requestedRowList
    : await findRowList(where, orderBy, pagination.page, pageSize)
```

範囲外のページ番号は、URL を手で書き換えたときにしか起きません。その稀なケースだけ 1 本ぶん損をして、通常時は 1 往復ぶん得をします。

結果は **クエリ 2 本、直列 2 往復**です。

### 3. `use cache` が 0 件だった

`next.config.mjs` には `cacheComponents: true` が入っています。Cache Components を有効にする設定です。実際の使用箇所も検索してみました。

```bash
grep -rn 'use cache' --include='*.ts' --include='*.tsx' apps packages | wc -l
# => 0
```

設定は追加していましたが、読み取り処理には使っていませんでした。画面を遷移するたびに DB を引いていたので、更新頻度の低いデータから見直しました。

というわけで、マスタ系の読み取りをキャッシュに載せます。

```ts
import { cacheLife, cacheTag } from "next/cache"

export const getCachedProductMasterFacet = async (organizationId: string) => {
  "use cache"
  cacheTag(productMasterCacheTag(organizationId))
  cacheLife("days")

  return getProductMasterFacet(organizationId)
}
```

無効化は書き込み側の Server Action でやります。ここで `revalidateTag` ではなく `updateTag` を選びました。

```ts
export async function saveProductMasterAction(slug: string, input: Input) {
  const membership = await requireProductMasterEditor(slug, input.productMasterId)
  // ...
  const result = await saveProductMaster(membership.organizationId, input)
  // ...
  updateTag(productMasterCacheTag(membership.organizationId))
  revalidatePath(`/organization/${slug}/product-master`)

  return { ok: true }
}
```

2 つの違いは公式ドキュメントに明記されています。

- `updateTag`: Server Action からのみ呼べる。次のリクエストは新しい値を待つ
- `revalidateTag`: Route Handler からも呼べる。`"max"` 指定なら古い値を返しつつ更新し、`{ expire: 0 }` なら即時に失効させる

今回は Server Action で保存した後、一覧に新しい値を表示したかったため、`updateTag` を使いました。

### 4. コネクションプーラーを挟む

DB への接続方法も見直しました。新しく接続する際には TCP や TLS の処理も必要なので、クエリの実行時間とは分けて考える必要があります。

Supabase のプーラー（transaction mode）に向けました。ここで、危うく記憶で断言しかけたことがあります。

以前使っていた `?pgbouncer=true` が今回も必要か確認するため、`@prisma/adapter-pg` の型定義を開きました。

```ts
/**
 * Optional function to generate names for prepared statements. (中略)
 * If not provided, prepared statements are not cached.
 */
statementNameGenerator?: StatementNameGenerator;
```

`statementNameGenerator` を渡したときだけ、名前付きの prepared statement を使います。渡していなければ使わないので、transaction mode のプーラーをそのまま通せます。

今回の Driver Adapter については、型定義を確認して判断しました。

なお、マイグレーション用の接続は別です。DDL はプーラー越しに流せないので、直接接続のまま置いておきます。

## キャッシュに載せる基準は「入口を数え上げられるか」

キャッシュするデータは、更新箇所を確認できるものに絞りました。どこで書き換わるか分からないと、保存後も古い値を返してしまうためです。

商品マスタについては、次のように書き込み処理を検索しました。

```bash
# 商品マスタを書き換える箇所を全部出す
grep -rn "productMaster\.\(create\|update\|delete\|upsert\|createMany\|deleteMany\)" \
  packages/features/src --include='*.ts' | grep -v spec
```

これで見落としをひとつ発見しました。**別機能の CSV 取り込みが、未登録の商品名を見つけると商品マスタ側のレコードを勝手に作っていた**のです。商品マスタの編集画面だけでなく、この取り込み処理でもキャッシュを無効化する必要がありました。

逆に、載せなかったものもあります。マスタ一覧に「この表を使って算出された件数」が含まれているケースです。この件数は別機能の書き込みのたびに変わります。無効化の入口が広すぎる。クエリ 1 本ぶんの得なので、割に合わないと判断して見送りました。

## 署名付き URL は表示時に発行する

画像つきの一覧では、署名付き URL の有効期限も考慮しました。

一覧はサムネイルを出すため、ストレージの署名付き URL を発行していました。この URL には有効期限があります。素直にキャッシュへ載せると、期限切れの URL を延々と配ることになります。

幸い、取得処理は「行を引く」と「URL を付ける」に分かれていました。そこで、**パスまでをキャッシュに載せ、URL は表示するページの分だけ毎回発行し直す**形にしました。

```tsx
// 重い問い合わせはキャッシュから。URL は毎回発行し直す
const rowList = await getCachedProductRowList(organizationId)
const { itemList, categoryList, ...page } = presentProductRowPage(rowList, query)
const productPage = {
  ...page,
  itemList: await attachThumbnailUrlList(itemList),
  categoryList,
}
```

絞り込みと並び替えも、キャッシュを跨がずにメモリ上でやります。引数を組織 ID だけにしておかないと、当たらない組み合わせが際限なく増えて、DB を引く回数が結局減りません。

## テストに止められた話

編集画面も、見出しとデータの表示を分けようとしました。見出しを先に出して、データだけ後から流し込む形です。

```tsx
export default async function ProductNewPage({ params }) {
  const { slug } = await params
  return (
    <div>
      <h1>新規作成</h1>
      <Suspense fallback={<FormCardSkeleton />}>
        <FormContainer slug={slug} /> {/* ここで権限を確認 */}
      </Suspense>
    </div>
  )
}
```

テストが落ちました。

```
FAIL  keeps new, import and edit pages away from viewers
  - []
  + [ "[slug]/product/new/page.tsx" ]
```

このリポジトリには、**編集画面の `page.tsx` が権限ガードを直接含むことを検査するテスト**がありました。ガードをコンテナへ移すと、権限のない閲覧者にも一瞬「新規作成」の見出しが見えてしまいます。「権限のないユーザーには画面の存在自体を知らせない」という約束を、テストが守っていたわけです。

以前用意したテストで、権限確認の位置が変わったことに気づけました。

ガードはページに残し、遅いクエリだけを切り出す形に直しました。所属の確認は 1 行の問い合わせなので、直列にしても大した損はありません。

## 変更後に確認したこと

今回、ミリ秒単位の前後比較は載せていません。数えたのは、画面あたりのクエリ本数と直列往復数だけです。

- 一覧画面: クエリ 5 本・直列 3 往復 → 2 本・2 往復
- マスタ系の読み取り: キャッシュに当たれば DB を引かない
- リージョン: `x-vercel-id` が `hnd1` であることを確認

この変更前後で画面全体の表示時間は測っていないため、改善率は出していません。

その実測を、この記事より前にやった回があります。コードの中だけを疑って、いちばん重いクエリを 375ms から 169ms に縮めた話です。**それでも体感は変わりませんでした。** ミリ秒の前後比較は、そちらに載せています。

https://zenn.dev/yoshinani_dev/articles/e7a41c9b3d5f28

今回はクエリの中身だけでなく、データを取りに行く場所と回数も見直しました。同じ構成の管理画面で待ち時間が気になる場合の参考になれば幸いです。
