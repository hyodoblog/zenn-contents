:::message
クライアント案件のリポジトリ名は伏せています。容量の数字は、`df`と`du`で実際に測った値です。
:::

1TBのMacBook Airで、ストレージの空きが8GBまで減っていました。

Claude Codeに「ストレージがほぼないので整理したい」と頼んで、何が容量を使っているかを調べてもらいながら掃除しました。原因はほとんどが開発まわりで、最終的に空きは約380GBまで戻りました。

最近はClaude CodeやCodexに作業を並列でお願いすることが多く、そのたびにGitのworktreeが作られます。このやり方だと溜まりやすいものがいくつか分かったので、消した順に紹介します。

## 何が容量を使っていたか

最初に`du`で大きい場所を調べた結果です。

| 場所 | サイズ |
| --- | --- |
| 各リポジトリの`.turbo`（167個） | 約170GB |
| Docker Desktopのディスク（`Docker.raw`） | 約115GB |
| `~/Library/Caches` | 約50GB |
| 各リポジトリの`.next` | 約47GB |
| pnpmのストア | 約45GB |
| npmのキャッシュ（`~/.npm`） | 約33GB |

`.turbo`だけで170GBあり、一番大きいものは1つのリポジトリで72GBありました。

消した順番と、`df`で測った前後の空き容量はこうなりました。ほかのアプリの書き込みでも値は動くので、目安です。

| 手順 | 空き容量 |
| --- | --- |
| パッケージマネージャのキャッシュ | 13GB → 62GB |
| Dockerのビルドキャッシュ・未使用イメージ | 62GB → 116GB |
| `.turbo`と`.next` | 116GB → 335GB |
| Xcodeのキャッシュなど | 335GB → 341GB |
| Dockerの未使用ボリューム | 341GB → 362GB |
| 使っていない`node_modules`とマージ済みのworktree | 356GB → 382GB |

最初に測ったときは8GBでしたが、掃除を始める直前には13GBになっていました。

## パッケージマネージャのキャッシュ

再ダウンロードすれば戻るものなので、まとめて消しました。

```bash
npm cache clean --force
pnpm store prune
uv cache clean
brew cleanup --prune=all -s
rm -rf ~/Library/Caches/Yarn ~/Library/Caches/pnpm ~/Library/Caches/pip \
  ~/Library/Caches/CocoaPods ~/Library/Caches/node-gyp
```

`pnpm store prune`は、どのプロジェクトからも使われていないパッケージだけをストアから消します。今回は15.6GB減りました。uvのキャッシュは7.6GB、Homebrewは1.9GBでした。

## Docker

`docker system df`で見ると、次の状態でした。

| 種類 | サイズ | 消せる分 |
| --- | --- | --- |
| イメージ | 63GB | 27GB |
| ビルドキャッシュ | 30GB | 21GB |
| ボリューム | 33GB | 21GB |

まず、停止中のコンテナ、ビルドキャッシュ、どのコンテナからも使われていないイメージを消しました。どれもビルドやpullをし直せば戻ります。

```bash
docker container prune -f
docker builder prune -a -f
docker image prune -a -f
```

なお、`Docker.raw`は`ls -l`で見ると1TBと表示されますが、これは上限のサイズです。実際の使用量は`du -sh`で確認できます。

### ボリュームを消しても、Macの空きがあまり増えなかった

次に、使われていないボリュームを消しました。ボリュームにはローカルDBのデータが入っていることがあり、消すと次の起動では空のDBから始まります。私の環境では未使用のボリュームが291個あり、案件ごとやworktreeごとに作られたDBのボリュームも含まれていました。

消す前に一覧をファイルに残しておくと、何を消したか後から確認できます。

```bash
docker volume ls -q -f dangling=true > unused-volumes.txt
xargs docker volume rm < unused-volumes.txt
```

`docker volume prune`でも消せますが、`-a`を付けないと名前付きのボリュームは対象になりません。

`docker system df`ではボリュームが24GB減ったのに、Macの空きは7GBしか増えませんでした。Docker DesktopはLinuxのVMを動かしていて、データは`Docker.raw`という1つのファイルに入っています。公式のFAQによると、VMの中で消した分がMacの空きに戻るまで、数分かかることがあります。

https://docs.docker.com/desktop/troubleshoot-and-support/faqs/macfaqs/

今回は待たずに、VMの中で`fstrim`を実行しました。

```bash
docker run --rm --privileged --pid=host alpine:3.20 \
  nsenter -t 1 -m -u -i -n fstrim -av
```

`Docker.raw`の実際のサイズは41GBから30GBになり、Macの空きは14GB増えました。FAQには、同じ目的のコマンドとして次が載っています。

```bash
docker run --privileged --pid=host docker/desktop-reclaim-space
```

## `.turbo`と`.next`

一番容量が空いたのがこれです。どちらもビルドすれば作り直されるので、全部消しました。

ただし、開発サーバーが動いているリポジトリの`.next`を消すと、そのサーバーが動かなくなります。先に動いているサーバーを確認して、3つだけは残しました。

```bash
# 動いている Next.js のサーバーと、その作業ディレクトリ
ps -axo pid,command | grep -E "next (dev|start)|next-server" | grep -v grep
lsof -a -d cwd -p <PID>

# .turbo と .next の一覧（node_modules の中は見ない）
find ~/Development \( -name node_modules -prune \) \
  -o \( -type d \( -name .turbo -o -name .next \) -prune -print \) > build-dirs.txt
```

`build-dirs.txt`から動いているサーバーの分を外してから消しました。

```bash
tr '\n' '\0' < build-dirs.txt | xargs -0 rm -rf
```

### Turborepoのキャッシュはworktreeからも集まってくる

`.turbo/cache`はTurborepoのローカルキャッシュです。公式ドキュメントによると、Gitのworktreeで`turbo`を実行したときも、キャッシュはメインのworktreeの`.turbo/cache`に書き込まれます。`turbo.json`で`cacheDir`を指定すると、この共有はなくなります。

https://turborepo.dev/docs/crafting-your-repository/caching

AIエージェントにworktreeで作業してもらうほど、そのビルド結果もメインの`.turbo`に溜まっていくことになります。

ローカルキャッシュは標準では自動で消えませんが、Turborepo 2.10から上限を決める設定が追加されています。

```json:turbo.json
{
  "cacheMaxAge": "7d",
  "cacheMaxSize": "10GB"
}
```

`cacheMaxAge`は指定した期間より古いものを、`cacheMaxSize`は合計が上限を超えた分を古い順に、`turbo run`の開始時に消します。値は例です。どちらもデフォルトは無効で、Turborepo 3.0から標準で有効にする予定とのことです。

https://turborepo.dev/docs/reference/configuration

## 使っていない`node_modules`

使っているプロジェクトの`node_modules`を消すと入れ直しが必要になるので、使っているものと使っていないものに分けました。判断に使ったのは次の4つです。

- 最後のコミット日
- 未コミットの変更があれば、そのファイルの更新日
- 最後に`install`した日（`node_modules/.modules.yaml`の更新日）
- 開発サーバーなどのプロセスが、そのディレクトリで動いているか

メインのリポジトリは30日、worktreeは7日動きがなければ「使っていない」としました。この基準で、146プロジェクトのうち80プロジェクト（うち74がworktree）の`node_modules`、561個を消しました。

### `du`では109GBあったのに、あまり空かなかった

消した`node_modules`は`du`の合計で109GBありましたが、Macの空きは十数GBしか増えませんでした（同時にworktreeの削除も進めていたので、正確には分けられていません）。

pnpmは、macOSではストアのファイルを「クローン」して`node_modules`を作ります（APFSのコピーオンライト）。

https://pnpm.io/settings/node-modules#packageimportmethod

クローンはデータの実体を元のファイルと共有しているので、`du`では2つ分に数えられますが、ディスクは1つ分しか使っていません。2GBのファイルで試すと、次のようになりました。

```bash
mkfile 2g a
cp -c a b      # APFS のクローンを作る
du -shc a b    # 合計 4.0G と表示される
```

| 操作 | 空き容量の変化 |
| --- | --- |
| クローン（b）を作る | ほぼ変わらない |
| クローン（b）を消す | ほぼ変わらない |
| 元のファイル（a）も消す | 2GB増える |

ストアに同じパッケージが残っている限り、`node_modules`を消してもほとんど空きません。worktreeの`node_modules`はメインのリポジトリとほぼ同じパッケージなので、消しても増えなかったのだと思います。

## マージ済みのworktree

Claude CodeやCodexに並列で作業してもらうと、worktreeがどんどん増えます。数えてみると、51リポジトリで107個ありました。一番多いリポジトリには37個あり、そのうち33個はサブエージェント用に作られたものでした。

次の条件をすべて満たすものだけを消しました。

1. マージ済み
   - worktreeのHEADが`origin/main`に含まれている
   - または、マージ済みPRのheadのコミットとHEADが一致している（squashマージの場合）
2. 未コミットの変更や未追跡のファイルがない
3. 3日以上動きがなく、プロセスやClaude Codeのセッションでも使われていない
4. Gitの管理外のファイル（`.env`など）が、メインのリポジトリと同じ内容

確認に使ったコマンドはこちらです。

```bash
# HEAD が origin/main に含まれているか
git merge-base --is-ancestor <HEADのコミット> origin/main && echo merged

# squash マージの場合は、マージ済み PR の head と比べる
gh pr list --state merged --limit 1000 --json number,headRefOid

# 未コミットの変更や未追跡のファイルがないか
git -C <worktree> status --porcelain

# 削除
git worktree remove <worktree>
git worktree prune
```

`git worktree remove`は、変更や未追跡のファイルがあると`--force`なしでは消せません。一方で、`.gitignore`で除外しているファイルは確認されずに一緒に消えます。`.env.local`をworktreeでだけ書き換えていると、それも消えてしまうので、4つ目の条件を入れました。

実際に、worktreeにしかない`.env.local`や作業用のスクリプトなどが見つかったものが11個あり、それらは残しています。

この条件で64個を消し、マージ済みであることを確かめたローカルのブランチも46本消しました。リモートのブランチはそのままです。

### 判定で間違えたところ

Claude Codeが最初に書いた判定スクリプトでは、ほとんどのworktreeが「使用中」になりました。`ps`で出したコマンドラインにworktreeのパスが含まれているかを見ていたのですが、裏で動いていた`node_modules`の削除コマンド（`rm -rf <パス>...`）自身に引っかかっていました。

また、Prismaの生成コードや`.eslintcache`も「worktreeにしかないファイル」に数えていたので、再生成できるものは比較から外しました。

## 余談

Claudeのデスクトップアプリにも、設定（Settings › This computer › Storage）に、しばらく使っていないセッションのworktreeを消す機能があります。ただ、基準は最後に使った日（30・60・90日）です。マージ済みかどうかで消したかったので、今回は自分で判定しました。

同じようにAIエージェントで並列開発していて、容量が足りなくなった方の参考になれば幸いです。
