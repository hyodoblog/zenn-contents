企業情報を集め、サイトを解析し、営業文面を作る BtoB の営業支援ツールを開発しています。作成した文面は、人が承認してから送信します。

最初は一覧や詳細、一括操作などの管理画面を作っていましたが、MCP 経由でも操作できるようにしたところ、画面を使う機会がかなり減りました。

今回は、MCP を追加するときに変更した承認処理と、運用して分かったことを紹介します。

:::message
本記事は業務システムの開発に伴走した記録です。クライアント名・プロダクト名・業務固有の用語は伏せ、テーブル名やツール名は一般的な名前に置き換えています。
:::

## MCP で操作するようになった背景

このツールでは、対象企業のうち公式サイトの URL を確認できたのは数 % で、メールアドレスを公開していない企業も多くありました。

そのため、画面の改善だけでなく、データソースの追加や判定精度、処理できる件数に開発時間を使いたいと考えていました。MCP で日常の操作ができるようになったので、管理画面に追加する機能も見直しています。

## 承認処理を共通化した

MCP を追加する際、操作経路によって承認の検査が違うことに気づきました。

このツールには「企業除外リスト」「送信抑止リスト」「送信根拠の有効期限」「日次上限」「静穏時間」といったガードがあります。承認の処理は当時 3 か所にありました。画面の Route Handler、MCP のツール、そして一括承認の Route Handler です。それぞれが似たコードを持っていました。

問題は一括承認でした。1 件ずつの承認はガードを通していたのに、**一括承認だけが通していなかった**のです。

| 操作 | 企業除外の確認 | 抑止リストの確認 | 送信根拠の鮮度 |
| --- | --- | --- | --- |
| 1 件ずつ承認 | ✅ | ✅ | ✅ |
| まとめて承認 | ✅ | ❌ | ❌ |

「まとめて承認」を選ぶだけで検査が緩くなる。担当者から見れば、どちらも同じ「承認」です。

直し方は素朴でした。状態遷移をアプリケーションサービスへ集約し、入口は `Actor` を組み立てて呼ぶだけの薄い層にしました。

```ts
/**
 * 操作者。画面（セッション）と MCP（API トークン）の違いを、ここで 1 つに揃える。
 *
 * アプリケーションサービスは Actor しか受け取らない。入口ごとに別の型を渡せてしまうと、
 * 「画面では効くが MCP では効かない検査」が生まれる。それを型で防ぐのがこの層の役割。
 */
export interface Actor {
  organizationId: string
  userId: string | null
  role: UserRole
  /** 操作経路。監査ログへ残して画面操作と MCP 操作を区別する */
  via: "ui" | "mcp"
}
```

そして一括処理は、1 件ずつの処理をそのまま順に呼びます。

```ts
/**
 * まとめて処理するときだけ検査を省く、ということをしないための作り。
 */
for (const draftId of draftIds) {
  try {
    succeeded.push(await approveDraft(actor, { draftId }))
  } catch (error) {
    failed.push({ id: draftId, error: message(error) })
  }
}
```

この変更で、画面・MCP・一括処理のいずれから呼んでも、同じ承認処理を通すようにしました。

## MCP から承認・送信する場合

とはいえ、当初は承認と送信だけは画面に残すつもりでした。要件の絶対条件として「送信の最終判断は必ず人間が行う」と決めており、運用の記録として、誰がいつ承認・送信したかを記録する必要があるからです。

MCP 経由にする場合も、人が内容を確認して実行を決める手順は残したいと考えていました。

証跡として必要なのは次の 3 つです。

1. 操作者が実在の人物として特定できること
2. 何を承認・送信したかが記録されていること
3. 承認から送信までの間に、人の意思が挟まっていること

MCP 側でも、この 3 点を確認できるようにしたいと考えました。

**1 について。** MCP の認証は API トークンですが、トークンは必ず実在の利用者へ紐づけます。失効・期限切れ・利用停止は弾きます。ここを緩めると「誰が承認・送信したか」を追跡できなくなり、証跡として成立しません。操作した利用者を記録するために、画面のセッションと MCP のトークンを同じ `Actor` に揃えています。

**2 について。** これは画面もチャットも変わりません。同じサービス層が同じ監査ログを書きます。`via` によって、画面と MCP のどちらから操作されたかも残しています。

**3 について。** ここが本題でした。送信ツールの入力スキーマを、こうしています。

```ts
confirmed: z
  .literal(true)
  .describe("送信対象と件数を利用者へ提示し、承諾を得た場合にだけ true を指定します")
```

宛先・本文・件数を提示し、利用者の承諾を得てから実行するよう、ツールの説明に書いています。

ただし、`confirmed: true` はモデル自身が指定できる値です。このスキーマだけで、人が確認したことまで証明できるわけではありません。承認の記録については、後から作ったチェックリストでも補足しました。

https://zenn.dev/yoshinani_dev/articles/756f59add7e761

チャットでは、送信対象とあわせて前回の送信日なども提示できます。今回の運用では、その情報を見ながら対象を確認しています。

## 一覧や設定値の確認

次に残ると思っていたのが、送信キューや操作ログの一覧です。50 件並んだ中から赤い行を 1 件見つけるのは目のほうが速い。これは今でもそう思います。

今回は、MCP で取得した結果をその場で表にして確認することもできました。

運用を始めてから、一覧で見たい列や集計軸が変わることがあります。そのたびに画面を改修するより、必要な情報を取得してチャットで確認するほうが、今回の使い方には合っていました。

ツールの戻り値にも、判断に使う情報を含めています。たとえば設定変更のツールは、変更後の設定に加えて「その設定で 1 日に実際に送れる件数」を必ず返します。

```ts
return {
  ...settings,
  // 上限を上げただけでは届かない場合があるため、実際に送れる件数を必ず返す
  sendCapacity: calculateSendCapacity(settings),
}
```

日次上限だけでなく、送信間隔と静穏時間によっても送れる件数が変わります。そこで、設定値とあわせて計算結果を返すようにしました。

集計軸を変えて何度か確認したい場面では、その都度表を作れるほうが便利でした。一覧画面に列を追加する前に、ツールの戻り値で必要な情報を渡せるかを確認しています。

## 管理画面も残している

MCP を使うには、利用者が対応するクライアントを使える必要があります。全員に同じ環境を用意できるとは限らないため、現在も管理画面は残しています。

どちらも同じサービス層を通す構成にしたので、操作する入口が違っても承認処理を共通にできます。

## ツールを追加した後に再接続が必要だった

運用していて、更新したツールが同じセッションから使えないことがありました。

新しい設定項目を追加してデプロイした直後、同じ Claude セッションから設定を変えようとすると、こう返ってきました。

```text
Input validation error: formFallbackToEmail: Invalid input: expected boolean, received string
```

サーバー側では新しい引数を boolean として受け付けていましたが、クライアントからは文字列が届いていました。

このとき使っていた MCP クライアントでは、接続時のツール一覧と入力スキーマが残っていました。手元のスキーマにその項目が無いため、値が boolean として型付けされずに送られていました。同じ理由で、新しく追加したツールはセッションのツール一覧に存在すらしませんでした。

サーバーのデプロイ後にセッションを開き直し、新しいツールと入力項目が使えることを確認しました。

Web アプリならリロードで済む話が、MCP ではセッションの再接続になります。本人には「使えない」としか見えないので、サーバー側の不具合と誤診しやすい。

この環境では、ツールを追加した際に利用者へ再接続を案内する必要がありました。

## まとめ

今回の営業支援ツールでは、MCP を追加したことで管理画面を使う機会が減りました。画面と MCP の処理を別々に持つと確認内容に差が出たため、承認処理は共通化しています。

今から同じ用途のツールを作るなら、まず必要な操作を MCP で用意し、画面が必要になったところから追加したいと考えてます。利用者の環境や操作内容によっても変わるので、今回の構成が参考になれば幸いです。
