2026年10月21日に Node.js のセキュリティリリースが出ました。修正は10件で、Brotli デコーダの範囲外書き込み（CVE-2026-111497、RCE のおそれ）や、TLS 証明書のホスト名チェックを回避できるものなど、High が4件あります。

https://nodejs.org/en/blog/vulnerability/october-2026-security-releases

修正版は **24.22.1 / 22.23.4 / 26.12.1** です。20系以前はサポートが終わっているので直りません。

私の手元には、受託案件と自社サービスを合わせて50ほどのリポジトリがあります。デプロイ先は主に Vercel（7チーム・125プロジェクト）で、ほかに Cloud Run と Firebase Functions が少しあります。これを Claude Code と一緒に調べて、2日かけて対応しました。

Node を上げる場所ごとに気をつけることが違ったので、その順に書いていきます。

## どこで Node が動いているかを洗い出す

最初に、Node が実際に動いている場所を数えました。

| 場所 | 調べたこと |
| --- | --- |
| 手元の Mac | mise で入れている Node の版と、常駐しているプロセスがどの Node で動いているか |
| 各リポジトリ | `engines.node`、`mise.toml`、CI の `node-version`、Dockerfile の `FROM` |
| Vercel | プロジェクト設定の Node と、本番ビルドのログに出ている実際の版 |
| Cloud Run | 動いているイメージのベース |
| Firebase Functions | `firebase.json` の `runtime` |

あわせて、今回の CVE に関係する機能（SEA・スタートアップスナップショット・Permission Model・Brotli を直接展開する処理）をコードから grep しました。どれも使っていなかったので、コード側の修正は不要でした。ただ `fetch()` は `Content-Encoding: br` の応答を自動で展開するので、外部の API を呼んでいるサービスはすべて Node の更新で直す必要があります。

## 手元の Mac

mise で Node 24 を使っているので、更新自体は1行です。

```bash
mise install node@24.22.1 && mise use -g node@24
```

これで `node -v` は v24.22.1 になりましたが、2つ見落としがありました。

1つ目は、**グローバルに入れていた npm パッケージが消えたこと**です。mise は Node の版ごとにインストール先が分かれているので、`vercel` や `typescript` は古い 24.18.0 側に残ったままでした。古い版の `lib/node_modules` から同じ版を入れ直しました。

```bash
npm install -g typescript@7.0.2 typescript-language-server@6.0.1 vercel@59.10.0
```

2つ目は、**動き続けているプロセスは古い Node のまま**だったことです。Claude Code や ChatGPT のデスクトップアプリが起動した MCP サーバーや言語サーバーは、何日も前に起動したまま 24.18.0 で動いていました。アプリを再起動して、どのプロセスも新しい Node で動いていることを `lsof` で確かめてから、古い Node をアンインストールしました。

ちなみに、アプリに同梱されている Node（ChatGPT アプリの v24.21.0 など）は自分では更新できないので、アプリのアップデート待ちです。

## Vercel：engines が効くのはビルドするディレクトリだけ

Vercel は、プロジェクト設定の Node（22.x / 24.x）より `package.json` の `engines` を優先します。ビルドログにもこう出ます。

```text
Warning: Due to "engines": { "node": ">=24" } in your `package.json` file, the Node.js Version defined in your Project Settings ("22.x") will not apply, Node.js Version "24.x" will be used instead.
```

125プロジェクトの本番ビルドのログを全部読んでみると、設定が 22.x のまま `engines` の上書きも効いておらず、Node 22 でビルドされていた本番が18件ありました。手元にリポジトリがあって理由まで調べられたものでは、原因は2つでした。

- monorepo で Vercel のルートディレクトリが `apps/web` になっていて、`engines` がリポジトリ直下の `package.json` にしか書かれていなかった。Vercel が見るのはルートディレクトリの `package.json` だけです。
- 最後の本番デプロイが、`engines` を足す前のコミットのままだった。

もう1つ気になったのが、`>=24` と書いていると出る次の警告です。

```text
Warning: Detected "engines": { "node": ">=24" } in your `package.json` that will automatically upgrade when a new major Node.js Version is released.
```

Vercel が Node 26 に対応した時点で、勝手にメジャー版が上がってしまいます。そこで次の3つをやりました。

- すべてのリポジトリで `engines.node` を `"24.x"` にする
- monorepo では、Vercel がビルドする `apps/*` の `package.json` にも書く
- Vercel のプロジェクト設定も、22.x のものを 24.x に切り替える

## Vercel：ビルド環境だけ先に直っていた

Vercel は告知で「22.x と 24.x はパッチ版を Vercel が管理するので、設定の変更は不要」と書いています。

https://vercel.com/kb/bulletin/node-js-security-advisory

ただ、修正版の配布は「進行中」で、既存のデプロイに再デプロイなしで当たるのかは書かれていませんでした。WAF で外からの攻撃は止めているものの、関数が外部から取ってくる応答は対象外とも書かれています。

分からないので、実行時の版を返すだけの関数を置いた確認用のプロジェクトを作って測りました。

```js:api/v.js
export default function handler(req, res) {
  res.status(200).json({
    runtime: process.version,
    brotli: process.versions.brotli,
    openssl: process.versions.openssl,
    undici: process.versions.undici,
  });
}
```

ビルド時の版も残すために、`build` スクリプトで `process.version` をファイルに書き出しておきました。2026年10月22日の結果はこうです。

| 設定 | ビルド時 | 実行時（関数） |
| --- | --- | --- |
| 24.x | v24.22.1 | **v24.21.0** |
| 22.x | v22.23.4 | **v22.23.2** |

新しくデプロイした直後でも、関数の実行環境は修正前でした。つまり、今すぐ全プロジェクトを再デプロイしても意味がありません。

この確認用のプロジェクトは消さずに残し、毎朝9時に実行時の版を測るスケジュールタスクを Claude Code に作ってもらいました。再デプロイなしで版が上がれば、既存のデプロイにも自動で当たっていると判断できます。上がらなければ、配布完了を待って再デプロイします。

## Cloud Run：自分でイメージを作り直す

Vercel のような自動のパッチは無いので、Cloud Run で動かしている Discord Bot はイメージを作り直す必要がありました。Dockerfile は `FROM node:22` のままで、`engines`（24）ともずれていました。

```dockerfile
# Node はパッチ版まで固定する。セキュリティリリースが出たらここを上げて再デプロイすること
FROM node:24.22.1
```

`node:24` のように浮かせておく手もありますが、再ビルドしないと上がらないのは同じなので、どの版で動いているかが Dockerfile を見て分かるようにパッチ版まで書きました。

手元で本番と同じ `docker build --platform linux/amd64` をして、イメージ内の `node -v` が v24.22.1 であること、シークレットなしで起動すると環境変数の検証まで進むことを確かめてから、dev → 本番の順にデプロイしました。

この Bot は最小インスタンス数が1なので、古いリビジョンのインスタンスが残って Discord に二重に接続しないかが気になりました。Cloud Monitoring の `run.googleapis.com/container/instance_count` を見ると、古いリビジョンは新しいリビジョンが立ち上がった約1分後に0になっていたので、そのままにしています。

## リポジトリの一括修正で踏んだもの

`engines` の変更は1行なので、Claude Code にスクリプトで一括で PR を作ってもらいました。最終的に PR は66本作り、65本をマージしました（1本は同じ変更が別のコミットで先に入っていたので閉じました）。単純な変更でしたが、いくつか踏んでいます。

**デフォルトブランチを取り違えた。** ローカルの `origin/HEAD` が古いままで、GitHub 上のデフォルトが `develop` に変わっていたリポジトリに `main` 向けの PR を出してしまいました。develop にも同じ変更を入れる PR を追加して直しています。PR を作る前に `git remote set-head origin -a` で取り直すべきでした。

**バージョン指定のファイルを二重に作った。** 「`mise.toml` が無い」と判断したリポジトリに足したら、実は `.mise.toml` や `.tool-versions` が最初からありました。探す前に足すと重複します。

**`--ignore-scripts` で Prisma のクライアントが消えた。** lockfile に差分が出ないかを確かめるために `--ignore-scripts` 付きで install したところ、postinstall の `prisma generate` が走らず、push 前のフックの lint が型エラーで落ちました。テストを流す前は普通に install します。

**zsh で `$def:turbo.json` が壊れた。** `git show $def:turbo.json` と書いたら `fatal: ambiguous argument 'mainurbo.json'` になりました。zsh では `:t` がパスの末尾を取り出す修飾子として解釈されるためです。`"${def}:turbo.json"` と書けば直ります。

## マージしたら本番ビルドが落ちた：Prisma の生成漏れ

`engines` の PR をマージしたら、いくつかの本番デプロイが次のエラーで失敗しました（直前の成功したデプロイが公開されたままなので、利用者への影響はありませんでした）。

```text
Error: Module not found: Can't resolve './generated/prisma/client'
```

今回の変更とは関係なく、前からある問題でした。ビルドログを成功したものと見比べると、違いはビルドキャッシュでした。

- キャッシュが無いとき：`pnpm install` で postinstall の `prisma generate` が走り、成功する
- キャッシュが復元されたとき：`pnpm install` が `Already up to date` で何もせず、postinstall も走らない。生成先は git 管理外なので、アプリのビルドが生成物を見つけられずに失敗する

Turborepo の `generate` タスクを用意して、`build` がその後に走るようにしました。生成物も `outputs` に入れて、turbo のキャッシュから戻るようにしています。

```json:turbo.json（抜粋）
{
  "tasks": {
    "generate": {
      "dependsOn": ["^generate"],
      "outputs": ["src/generated/**"]
    },
    "build": {
      "dependsOn": ["^generate", "^build"],
      "outputs": [".next/**", "!.next/cache/**"]
    }
  }
}
```

手元では、生成物を消して `turbo run generate` を2回流し、2回目はキャッシュから生成物が戻ることを確かめました。Prisma を使っているほかのリポジトリも調べたところ、`@repo/schema#build` の `outputs` に生成先が入っていて対策済みのものが多かったです。

ちなみに、ある Vercel プロジェクトではマージ後のデプロイ自体が走りませんでした。変更が `turbo.json` だけで、ルートディレクトリ（`apps/web`）の外だったので、Vercel が変更なしとして省いたようです。修正が効くかは、main からプレビューを1回作って確かめました。ビルドキャッシュが復元された状態でも `generate` が先に走って Ready になっています。

## 直す前に本番が何をビルドしているかを見る

ある案件では、Vercel の Git 連携のビルドが毎回 `No Next.js version detected` で失敗していました。main には静的な HTML しか入っていなかったので、Claude Code は最初「Framework Preset を Other にすれば直る」と提案していました。

本番の成功したデプロイのログ（`vercel inspect --logs`）を見ると、実際は Next.js のアプリがビルドされていました。アプリのソースは GitHub に push されていないローカルのブランチにあり、そこから `vercel deploy` で手動で出していたためです。Framework Preset を変えていたら本番が壊れていました。

ブランチを push して main に取り込み、Git 連携のビルドで本番が出るようにしました。

## 対応の結果

| 場所 | 状態 |
| --- | --- |
| 手元の Mac | Node 24.22.1 だけ。常駐プロセスも新しい Node で動いている |
| リポジトリ | Node の指定（engines・mise・CI・Dockerfile）をすべて Node 24 系にそろえた |
| Vercel | プロジェクト設定はすべて 24.x。関数の実行環境は、Vercel の配布待ち |
| Cloud Run | `node:24.22.1` で作り直して本番に反映 |

Vercel の実行環境が修正版になったら、22.x から切り替えた18件を再デプロイして、確認用のプロジェクトを消せば終わりです。

ほかにも、Node 16 のまま残っていた古いプロジェクトを1つ消しました。Firebase Functions（`nodejs22`）のリポジトリは別に確認が必要なので、今回は保留にしています。

## Claude Code に任せたところ

調べる作業はほぼ Claude Code に任せました。50ほどのリポジトリの `engines` や CI の読み出し、Vercel の125プロジェクトのビルドログの確認、一括 PR のスクリプトなどです。

一方で、PR のマージと他チームの Vercel の設定変更は、Claude Code の自動承認の安全チェックで止められました。そこは Claude Code にスクリプトを作ってもらい、私が自分で実行しています。
