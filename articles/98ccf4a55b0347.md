LINE の Flex Message で作った承認カードが、特定の端末でだけ下端が切れて、承認ボタンが押せなくなりました。7 回直して 7 回とも再発しました。

犯人は「高さを削れば直る」という思い込みでした。実際に測ってみたら、短くしたほうが切れるという結果が出ます。

同じ症状で消耗している人の時短になれば嬉しいです。

![1バブルに詰めると下端のボタンが切れる。3バブルに分けると本文の長さに依存しなくなる](/images/line-flex-bubble-split.png)

:::message
本記事は業務システムの開発に伴走した記録です。クライアント名・様式名・ユーザー ID などは伏せ、サンプルデータは架空の稟議書に置き換えています。
:::

## つくっていたもの

LINE 上で完結する稟議申請システムです。申請者が LINE から申請すると、決裁者に Flex Message で承認依頼カードが飛び、その場で「承認する」「却下する」を押せます。

技術構成はこんな感じです。

- **アプリ**: Next.js（App Router）on Vercel。LIFF で申請フォーム、Messaging API で通知
- **データ**: Supabase（Postgres）

承認カードには、申請者名・様式名・申請日時・申請内容の各項目・承認ボタンを載せていました。

## 事件発生：ボタンが押せない

ある利用者から「承認ボタンが押せない」と連絡が来ました。手元の端末では再現しません。

その端末で見せてもらうと、カードの下端が途中で切れていて、最下段のボタンが画面に出ていませんでした。しかも Flex のバブルはスクロールしません。切れた先は指でも引っぱり出せない。

該当端末は、LINE の有料プランで提供されるカスタムフォントを設定していました。

## 7 回の敗北

ここから修正が始まります。履歴を並べるとこうなります。

| # | やったこと | 結果 |
|---|---|---|
| 1 | 受付 ID 行・確認ボックス・案内文を削除して短縮 | 再発 |
| 2 | フッター下パディングを 16px → 32px | 再発 |
| 3 | さらに 32px → 48px | 再発 |
| 4 | 末尾の案内文と区切り線を削除 | 再発 |
| 5 | body の下パディングを 20px → 30px | 再発 |
| 6 | 下パディングを 30px → 40px | 出したが取り下げ |
| 7 | 承認・却下ボタンを縦積みから横並びへ | 再発 |

コミットメッセージにはどれも「解消」と書いてあります。そして次のコミットで再発しています。

なぜこうなったのか。技術ではなく進め方の問題でした。

その端末で確認する手段が、本番マージ以外になかったのです。だから毎回「たぶんこれで直る」を本番へ投げ、報告を待ち、また投げる。検証していないので、外れても外れたと分からない。分からないまま次の仮説を積む。7 回ぶんの「解消」は、全部この繰り返しでした。

## 転機：シミュレータから実機にテスト送信できる

ここで [Flex Message Simulator](https://developers.line.biz/flex-simulator/) にテスト送信機能があったことを思い出しました。2021 年に追加されています。

デプロイなし・コード変更なしで、任意の Flex JSON を自分の LINE へ飛ばせます。

手順はこれだけです。

1. LINE で「Flex Message Simulator」公式アカウントを友だち追加する
2. シミュレータの `Send...` → `Register destination` を開く
3. 表示された QR コードをスキャンし、届いた認証コードを入力する
4. `View as JSON` に JSON を貼り、`Apply` → `Send...` → `Send`

ひとつ注意点があります。登録は再現する端末でやってください。手元の通常端末で登録すると当然きれいに表示されてしまい、検証がまるごと空振りになります。

これで「本番マージ = 検証」のループが切れました。1 回あたり数十秒です。

## 合否を目視で判断しない

回し始めてすぐ困ったのが判定です。「切れているかどうか」を毎回目で見て決めるのは曖昧です。確認を人に頼むときの説明も面倒になります。

そこでバブルの末尾に緑色の END マーカーを置きました。

```json
{
  "type": "box",
  "layout": "vertical",
  "backgroundColor": "#06C755",
  "cornerRadius": "md",
  "paddingAll": "8px",
  "contents": [
    {
      "type": "text",
      "text": "OK V2 END",
      "color": "#FFFFFF",
      "weight": "bold",
      "size": "sm",
      "align": "center"
    }
  ]
}
```

マーカーが完全に見えれば合格、切れていれば不合格。判断が要らないので「これ届いた画像そのまま送って」で済みます。

## 定規で高さの予算を測る

次に、そもそも何行入るのかを測りました。`size: sm` のテキストを 45 行並べただけのバブルを送ります。

```json
{ "type": "text", "text": "01", "size": "sm" },
{ "type": "text", "text": "02", "size": "sm" },
```

38 行目で切れました。上限はおよそ 39 行。ここから先は「収まるかどうか」を勘ではなく行数で議論できます。

## 実測結果

同じ申請データで、構成を変えた 7 パターンを送りました。

| 変種 | 構成 | paddingAll | 結果 |
|---|---|---|---|
| 現行 A | 本文とボタンが同じバブル | 20px | 最終項目で切断 |
| 現行 B | ボタン専用の小さいバブル | 16px | 完全表示 |
| V0 | 定規（sm 45 行） | 20px | 38 行目で切断 |
| V2 | 見出しを圧縮 | 20px | 完全表示 |
| V3 | 最大限に圧縮 | 16px | 切断 |
| V4a | 分割・前半 | 20px | 完全表示 |
| V4b | 分割・後半 | 20px | 完全表示 |
| V5 | V3 に `scaling` を追加 | 16px | 切断 |

### `scaling: true` は悪化させる

`scaling` は Flex Message の公式プロパティで、こう説明されています。

> If you set the `scaling` property to `true` of a Flex Message button, text, or icon, you can automatically scale the font size and icon size according to the font size setting of the LINE app.

「フォント設定に対応するための機能」と読めるので、この症状の解決策に見えます。私も最初はそう思いました。

実際はアプリのフォントサイズ設定に**追従させる**オプトインです。デフォルトは `false`。有効にすると、大きいフォント端末ではバブルがさらに高くなります。V5 はレイアウトを V3 と揃えて `scaling` だけ足したものですが、同じように切れました。

隣に用意されている `adjustMode: "shrink-to-fit"` も幅方向にしか効きません。しかも公式に、はっきり但し書きが付いています。

> The `adjustMode` property takes a "best-effort" approach that may work differently—or not at all!—on some platforms.

### パディングを厚くする対処は無意味だった

16px → 32px → 48px と積み増した 3 回は、すべて空振りでした。

書いてしまえば当たり前で、パディングを足せばバブルは高くなります。高さ超過が原因なら、悪化させる方向に押していたことになります。

### 短くすれば安全とは限らない

ここが一番おもしろかったところです。

V3 は V2 より明確に短いのに、V3 だけが切れました。

![情報量の多いV2は完全表示され、より短いV3はENDマーカーが切れた](/images/line-flex-shorter-clipped.png)

V3 は V2 から緑のボックスを撤去し、タイトルを `lg` から `md` に落とし、見出しを 1 つ削り、行間も詰めたものです。情報量は V2 のほうが多い。それでも結果は逆でした。

単純な「高さ上限」モデルでは説明がつきません。きれいに効いている相関はひとつだけでした。

- 合格した 3 つ（V2 / V4a / V4b）は `paddingAll` が `20px`
- 不合格の 2 つ（V3 / V5）は `paddingAll` が `16px`

パディングを減らしたほうが切れています。高さの見積もりと実際の描画で、パディングの扱いが食い違っている疑いがあります。

サンプルは 5 つなので、原因の断定はできません。それでも実務的にはこれで十分でした。高さを削るというアプローチが信用できない、と分かればいい。7 回直して 7 回再発した理由も、ここで腑に落ちました。

## 採用した構成

再現性があったのは「バブルを分ける」ことだけです。4 回試して 4 回とも通りました。

そこで承認依頼を 3 通に分割しました。

```
通1: 概要（申請者・様式名・申請日時）
通2: 申請内容の各項目
通3: 承認・却下ボタン
```

ボタンだけの短いバブルなら、本文がどれだけ伸びても巻き添えを食いません。

## 可変長への備え

申請項目はフォーム定義によって変わります。自由記述が長ければ、1 項目が 3 行や 4 行に膨らみます。項目数を数えるだけでは安全側に倒せません。

そこで、推定行数が予算を超えたら本文バブルをさらに分割するようにしました。

```ts
/** 実測上限は size:sm 換算で約39行。分割判定は安全側に倒して 28 行で切る。 */
const HEIGHT_BUDGET_LINES = 28
/** mega バブル・size:sm・大きいフォント端末での 1 行あたり全角文字数の目安。 */
const CHARS_PER_LINE = 18

function estimateWrappedLines(text: string): number {
  return Math.max(1, Math.ceil(text.length / CHARS_PER_LINE))
}
```

各ブロックに推定行数を持たせておき、予算を超えたら次のバブルへ送ります。あふれたぶんは「申請内容（続き）」として続きのバブルに出ます。

## テストは「症状」ではなく「ルール」を固定する

もともとのテストはこうなっていました。

- フッターが `horizontal` であること
- 申請者名が `xxl` であること
- 受付完了カードに案内文がないこと

どれも対症療法の結果を写しただけで、守りたい約束を表していません。おかげで設計を変えるたび、全部書き直す羽目になりました。

そこで、ルールそのものを検証する内容へ差し替えました。

```ts
// ルール: アクション可能な要素は本文と同じバブルに置かない。
for (const message of messages.slice(0, -1)) {
  expect(JSON.stringify(message)).not.toContain('"type":"button"')
}

// 16px の構成が実機で見切れたため、パディングは 20px を下限とする。
expect(Number.parseInt(body?.paddingAll ?? "0", 10)).toBeGreaterThanOrEqual(20)

// 長文でも 1 バブルに詰め込まず、内容も失わない。
expect(messages.length).toBeGreaterThanOrEqual(4)
expect(JSON.stringify(messages)).toContain(long)
```

## 公式ドキュメントに書いてあること、書いていないこと

書いてあるのはこのあたりです。

- 端末の OS・LINE バージョン・解像度・言語設定・フォントで描画が変わりうる
- `scaling` / `adjustMode` / `maxHeight` / `maxWidth` の仕様と対応バージョン

一方で、バブルの最大高さ、スクロールの有無、上限を超えたときの挙動は見つけられませんでした。

つまりレイアウトは保証されていません。公式が示す対処も「シミュレータで事前に確認せよ」に尽きます。プロパティで殴るより構造で依存を断つ。この方針は、公式の態度と照らしても妥当だと思っています。

## おわりに

7 回の再発を招いたのは、難しさではなく検証手段の不在でした。最初にシミュレータのテスト送信を用意していれば、1 回で終わっていたはずです。

Flex Message でレイアウトに悩んだら、プロパティ表を眺める前に、まず自分の端末へ 1 通投げてみてください。
