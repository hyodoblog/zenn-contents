以前、業務ツールの承認処理を見直していたら、1 件ずつの承認では通している検査が、一括承認では抜けていました。同じ「承認」なのに、まとめて押すと条件が緩くなる。自分たちで作ったコードの話です。

監視の通知が止まり、その裏でログの課金が膨らんでいたこともあります。こういう経験を記事に書いてきたのに、次のシステムで確認する項目へ落とさないのはもったいない。

そこで、SaaS・業務システム向けに **140 項目のセキュリティチェックリスト**をまとめました。過去の記事で扱った失敗と、国際基準を照らし合わせています。先に表を使いたい方は、[GitHub の詳細版](https://github.com/hyodoblog/zenn-contents/blob/main/docs/security-checklist/checklist.md)からどうぞ。

:::message
事例は過去に公開した記事の範囲で紹介しています。クライアント名・業務固有の用語は伏せています。チェックリストは汎用の評価用テンプレートで、特定のシステムの監査結果ではありません。
:::

## 一括承認だけ、検査を素通りしていた

MCP の記事を書いたときの話です。画面からの承認、MCP からの承認、一括承認。それぞれに似た処理がありました。

1 件ずつなら、除外対象や送信を抑止する条件を確認しています。ところが一括承認では、一部の確認が抜けていました。画面を触って正常に承認できることだけ見ていたら、見つからない種類の不備です。

そのときは、状態を変える処理とガードを同じサービスへ集めました。画面も MCP も一括処理も、そこを通します。

https://zenn.dev/yoshinani_dev/articles/a4c592b2b23ed7

今回の表では、これを **04-01「すべての経路で認可する」**の確認方法に入れています。通常の API だけでなく、MCP、一括操作、バッチでも同じ対象を拒否できるか試します。

もうひとつ、承認については補足があります。ツールに `confirmed: true` が届いただけでは、人が内容を見て承認した証拠にはなりません。その値をモデル自身が指定できるからです。

重大な操作では、誰がどの対象・内容を承認したかをサーバー側の記録に結び付けます。承認後に宛先や金額が変わったら、元の承認で通さない。この確認を 15-06 に加えました。[OWASP の取引承認の指針](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html)も参照しています。

## 通知が来ない間に、請求が増えていた

Google Cloud の請求が 1000 万円を超えた件も、以前の記事に書きました。エラーを知らせるために作った仕組みで、通知が止まっていました。その一方で、エラーログが大量に出て課金が積み上がっていました。

通知が静かだからといって、正常とは限りません。ここは私が実際に痛い目を見たところです。

https://zenn.dev/yoshinani_dev/articles/f30274290511a1

この経験から、11-08 は「監視しているか」で終わらない内容にしました。通知先を一時的に落とし、別の経路で異常に気づけるか。通知の失敗が、さらに同じ通知を呼ぶループにならないか。そこまで確かめます。

費用については、07-06 の確認にも含めています。**予算を知らせる仕組みと、処理を止める仕組みは分けて確認します。** Google Cloud の通知だけを行う予算設定は、自動で利用額を制限しません。[Cloud Billing の公式説明](https://docs.cloud.google.com/billing/docs/how-to/budgets)

停止機能を使う場合も、対象サービスと停止までの遅延、業務への影響を確認します。通知のメールが届いた、だけで終わらせないための項目です。

## 決済ボタンを連打しなくても、二重に払えてしまう

2022 年には、Stripe Checkout の URL が複数残り、別のタブから決済されるケースを書きました。スマホで URL を作り、PC でも開く。ひとつの画面でボタンを無効化しても、それだけでは防げません。

https://zenn.dev/yoshinani_dev/articles/bd996b5737b5b5

当時の記事では、残っている Checkout URL を失効させる対策を紹介しています。ただ、今回の確認表では、そこでチェックを付けて終わりにはしません。

一覧を取得し、既存の URL を失効させ、新しい URL を作る。その処理自体が同時に走れば、別々の URL ができる余地があります。注文を確定する側の制約も必要です。

06-07 には、同じ要求の再送に加えて、**同じ注文に対する別の要求が並行するケース**を入れました。別タブ、別端末、応答が返る前のタイムアウトを試します。

Stripe の冪等キーは、同じ要求を再試行する際に使う仕組みです。別々のキーで作った決済まで、自動でひとつになるわけではありません。注文 ID と決済の対応、状態遷移も合わせて確認します。[Stripe：Idempotent requests](https://docs.stripe.com/api/idempotent_requests)

## 性能改善やビルドの話も、確認表に残す

セキュリティという題名で書いた記事以外にも、使える知見がありました。

| 過去の記事で確認したこと | 今回、試験に含めること | 項目 ID |
| --- | --- | --- |
| [キャッシュの更新経路を調べたら、別機能の CSV 取り込みが見つかった](https://zenn.dev/yoshinani_dev/articles/3f9a1c7e08b24d) | 画面以外の更新、権限変更、顧客切替後にも古い値や他者のデータが残らないか | 05-03 |
| 同じ記事で、署名付き URL の期限とキャッシュの扱いを検討した | URL の期限切れと、権限を失った後に取得できる期間を確認する | 08-05 |
| [本番のビルドでロックファイルが無視され、依存が再解決されていた](https://zenn.dev/yoshinani_dev/articles/b66uxw1wbwf554) | CI が使った実際のバージョンを記録し、lockfile の不一致で止まるか | 10-05 |

署名付き URL は、期限内なら誰が持っていても使える設計があります。その場合、アプリで権限を外すだけでは発行済み URL は止まりません。必要な失効時間に合わせて、短い期限や認可付きの配信経路を選びます。

ロックファイルも、リポジトリに置くだけでは確認になりません。以前のビルドログには `Ignoring lockfile` と出ていました。今回は、CI で実際に読まれたかまで見ます。

たとえば pnpm では、次の指定を使えます。

```bash
# lockfile と manifest が食い違う場合は、依存を再解決せず停止させる
pnpm install --frozen-lockfile
```

この挙動は [pnpm の公式ドキュメント](https://pnpm.io/cli/install#--frozen-lockfile)で確認できます。別のツールでも、同じように「不一致で止まるか」を確認します。

過去記事の事実と、そこから今回追加した試験は、[事例と項目の対応メモ](https://github.com/hyodoblog/zenn-contents/blob/main/docs/security-checklist/field-notes.md)に分けて記録しました。昔のコードをそのまま持ち込むための表ではなく、次に同じ見落としをしないための材料です。

## 公開前に、まず確認する表

共通の項目は、認証・権限・顧客間の分離から、開発・運用・復旧まで 15 分野で 120 項目です。ISMS 向けの 20 項目を合わせて、全部で 140 項目あります。

ここでは、先に見たい項目を抜粋します。右端の ID で詳細版と照合できます。

| 確認 | 合格条件の要点 | 証跡の例 | 詳細 ID |
| --- | --- | --- | --- |
| 管理者の認証 | 管理画面、クラウド、コード管理、CI/CD で MFA を強制する | MFA 未登録時の拒否結果 | 03-01 |
| 他人のデータ | ID を変えても他人・他部署・他顧客を参照、更新できない | 複数アカウントの否定テスト | 04-02 |
| 管理者機能 | 一般利用者が管理 API や全件出力を実行できない | ロール別の拒否結果 | 04-03 |
| 承認・確定 | 担当外の操作や段階飛ばしで確定できない | 状態遷移の試験 | 04-07 |
| 顧客間の分離 | DB 以外のキャッシュ、検索、ジョブでも境界を保つ | 顧客を切り替えた試験 | 05-02〜04 |
| 二重処理 | 並行実行や再送で二重承認、二重請求、二重計上を起こさない | 同時要求と再試行の試験 | 06-07 |
| Webhook | 不正署名を拒否し、同じイベントを重複処理しない | 改ざん・再送の試験 | 07-04〜05 |
| 秘密情報 | リポジトリ、配布物、ブラウザへ秘密キーを埋め込まない | 履歴と成果物のスキャン | 08-03 |
| 添付の保護 | 未認証や権限のない利用者へファイルを返さない | 直接 URL も含む取得試験 | 08-05 |
| 重大な脆弱性 | 実際の悪用状況と公開範囲を踏まえ、重大な未対処を残さない | 対応台帳と再検証 | 10-06 |
| 実際の復元 | 復元後に重要業務を実行できる | 復元時間と整合性の確認 | 12-04 |
| 事故の初動 | 封じ込め、証拠保全、連絡、通知判断の担当が決まっている | 連絡試験と机上演習 | 12-06〜07 |

この表は全項目の抜粋です。ここを通ったあと、残りの適用項目も評価します。AI を使っていないなら AI の項目は対象外にできますが、未実装だから対象外、という扱いにはしません。

## ISMS の担当者と、一緒に埋める部分

ISMS を取得している会社で使うなら、会社の要求にも合わせる必要があります。技術側が「これで十分」と決めてしまうと、社内規程との食い違いが残ります。

最初に確認するのは、認証の範囲、最新の適用宣言書、社内のセキュリティ規程です。適用宣言書には、その会社が採用する管理策などが記載されています。[ISMS-AC の説明](https://isms.jp/isms/)

たとえばログの保存期間が規程で決まっていたら、その期間を設定と記録で確かめます。監査や権限の棚卸しも、会社ですでに回している手順につなげます。

追加した 20 項目は、この照合に使います。

| 追加する確認 | 実際に照合するもの | 詳細 ID |
| --- | --- | --- |
| 認証・適用の範囲 | 認証書、対象業務、拠点、開発・運用・委託の境界 | ISMS-01〜02 |
| 会社の管理策・規程 | 適用宣言書の版、社内基準、具体的な設定値と試験 | ISMS-03〜04 |
| 資産・リスク・例外 | 台帳、リスク評価、対応計画、残余リスク、例外期限 | ISMS-05〜08 |
| 目標・外部委託・人 | 評価指標、委託先の承認、ID・端末・教育の適用 | ISMS-09〜11 |
| 変更・運用・復旧 | リリース、定期点検、事故報告、業務継続との整合 | ISMS-12〜15 |
| 証跡と文書 | 承認、版管理、閲覧権限、保存期間 | ISMS-16 |
| 監査と改善 | 内部監査、不適合の是正、経営層のレビュー | ISMS-17〜19 |
| 利用・提供の判断 | 社内の必須条件、未達事項、承認、認証表示の範囲 | ISMS-20 |

社内で必須の条件なら、共通表の優先度にかかわらず確認します。例外が必要な場合も、開発担当だけで判断せず、会社の手続に沿って担当と期限を決めます。

認証書があることと、このシステムを確認し終えたことは別です。会社の文書と実装を対応付ける欄も、詳細版に用意しました。

## 全部に丸を付けなくていい

結果は、適合・一部適合・不適合・未評価・対象外の 5 種類にしました。

証拠がなければ未評価です。担当と次の確認日を書いておけば、何が残っているかは伝わります。新しいシステムで、まだ定期運用の実績がない場合も同じです。

優先度は、この表では次のように扱います。

| 優先度 | 扱い |
| --- | --- |
| P0 | 公開・顧客データ投入前に確認する基本統制 |
| P1 | 原則として正式提供前に整える標準統制 |
| P2 | リスクと契約に応じて強化する統制 |

これは本表の初期基準です。法令、契約、会社の ISMS で必要な条件と期限を優先します。

適用する P0 に不適合・一部適合・未評価が残る場合は、公開可と判定しません。「他人の添付が読めるか未確認」なら、ほかの行が埋まっていても先にそこを見ます。

例外として運用する場合も、結果を適合に書き換えません。残っている問題と、それを期限付きで受け入れた判断の両方を残します。

## 国際基準は、見落としを探すために使う

自分の失敗だけ集めても、経験していない種類の問題は抜けます。そこで、次の基準も参照しました。

| 基準 | 今回の使い方 |
| --- | --- |
| [NIST CSF 2.0](https://www.nist.gov/publications/nist-cybersecurity-framework-csf-20) | 統治、特定、防御、検知、対応、復旧を通して全体を見る |
| [ISO/IEC 27001:2022](https://www.iso.org/standard/27001) | 会社のリスク管理、管理策、運用、改善につなぐ |
| [OWASP ASVS 5.0.0](https://owasp.org/www-project-application-security-verification-standard/) | Web アプリの技術的な検証を具体化する |
| [OWASP API Security Top 10 2023](https://owasp.org/www-project-api-security/) | API 固有の主要リスクを補助点検する |
| [CSA CCM / CAIQ v4.1](https://cloudsecurityalliance.org/artifacts/cloud-controls-matrix-v4-1) | クラウドの責任分担と顧客への説明を整理する |
| [CIS Controls v8.1](https://www.cisecurity.org/controls/v8-1) | 資産、設定、端末、アクセスなどの運用を確認する |
| [NIST SSDF 1.1](https://csrc.nist.gov/pubs/sp/800/218/final) | 開発工程とソフトウェアの供給網を確認する |

参照の確認日は 2026 年 9 月 5 日です。各項目の詳細な出典は GitHub に載せています。

ただし、この表は規格本文の代わりにはなりません。ASVS L2 の適合を示すなら、そのレベルの適用要件を別途すべて確認します。国や業界ごとの要求も、対象に合わせて追加してください。

## 手元のシステムで使うなら

[評価記録テンプレート](https://github.com/hyodoblog/zenn-contents/blob/main/docs/security-checklist/assessment-template.md)を、社内の保管先へコピーしてください。最初にサービス名、環境、対象の版を記入します。

次に、P0 の行を開発と運用で分担します。ISMS の対象なら、規程との照合は管理責任者と進めます。設定画面や試験結果へのリンクを付け、確認できない箇所には担当と期限を残します。

記入済みの表には、内部の構成や弱点も載ります。公開 GitHub に戻さず、社内の権限管理された場所で保管してください。

## おわりに

一括処理を足す。キャッシュを入れる。監視を作る。どれも、そのときは必要だと考えてやったことです。その変更で確認すべき場所が増えているのに、元の動作確認だけで終えると取りこぼします。

過去の記事を読み返すと、そういう見落としが何度も出てきました。せっかく記録があるので、次のレビューで使える形にしておきます。

まずは 04-01 の行で、同じ操作をする入口を挙げてみてください。画面と API だけでなく、一括処理や MCP、バッチも含めます。以前の私たちのように、どこかひとつだけ違う実装になっていないか。そこから確かめてもらえると嬉しいです。
