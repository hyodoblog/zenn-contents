SaaS や業務システムを作っていると、「セキュリティは大丈夫ですか」と聞かれます。ログインはあります。通信も暗号化しています。でも、その説明だけでどこまで確認できたのかは伝わりません。

そこで、**合格条件・確認方法・証跡まで書いた、140 項目のチェックリスト**を作りました。共通の 120 項目と、ISMS 取得企業向けの追加 20 項目に分けています。

この記事に主要な確認表を載せ、全項目と記入用テンプレートは GitHub で公開します。公開前の点検や、開発担当と ISMS 担当が同じ表を見て話すときに使ってください。

:::message
業務システム向けに整理したチェック項目を、汎用のテンプレートとして公開しています。クライアント名や個別システムの構成は掲載していません。項目数は数えていますが、特定のシステムが合格したという監査結果ではありません。
:::

## 「対策している」だけでは、チェックが終わらない

表の形を考えるときに、気をつけたことがあります。

> 「アクセス制御がある」にチェックを付けても、他人の添付を開けないことまでは確認できていない。

ログインできることと、見てよいデータだけが見えることは別々に確認します。バックアップも同じです。取得が成功していることと、業務を再開できることは確認する対象が違います。

そこで、各行には「何があれば合格か」と「どう確かめるか」をセットで書きました。

| 曖昧な確認 | 今回の表で確認すること | 残す証拠の例 |
| --- | --- | --- |
| 認可がある | 別の利用者の ID に変えても、データを参照・更新できない | ID を差し替えた拒否テスト |
| 添付が非公開 | 未認証、他人、期限切れの経路から取得できない | ファイル取得の否定テスト |
| Webhook を使っている | 署名が不正なら状態を変えず、再送でも二重処理しない | 改ざん・重複イベントの試験 |
| バックアップがある | 復元後にログインでき、データと添付が整合している | 復元時間と照合結果 |

これは、認可を各リクエストで検証するという OWASP の考え方を、実際の試験に落としたものです。[OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

## 共通チェックは、15 分野で 120 項目

Web アプリだけを点検しても、運用端末や委託先の問題は残ります。技術と運用を同じ一覧で追えるように、各分野を 8 項目ずつ整理しました。

| 分野 | 主に見るもの | 詳細版の ID |
| --- | --- | --- |
| ガバナンス・資産・リスク | 責任者、資産台帳、データフロー、リスク受容 | 01-01〜08 |
| データ・プライバシー | 分類、収集目的、保存期間、削除、外部送信 | 02-01〜08 |
| 認証・セッション | MFA、パスワード、復旧、失効、Cookie | 03-01〜08 |
| 認可・業務上の境界 | 他人のデータ、権限昇格、出力、承認順序 | 04-01〜08 |
| SaaS の顧客間分離 | DB、キャッシュ、検索、ジョブ、顧客管理 | 05-01〜08 |
| アプリ・業務処理 | 入力検証、注入、XSS、CSRF、二重処理 | 06-01〜08 |
| API・外部連携 | トークン、OAuth、署名、再送、利用制限 | 07-01〜08 |
| 暗号化・秘密・ファイル | TLS、鍵、秘密情報、添付、出力処理 | 08-01〜08 |
| クラウド・構成 | 公開範囲、環境分離、更新、DNS、安全設定 | 09-01〜08 |
| 開発・脆弱性 | レビュー、CI/CD、依存部品、診断、修正期限 | 10-01〜08 |
| ログ・監視 | 誰が何をしたか、保管、検知、通知の到達 | 11-01〜08 |
| 復旧・事故対応 | RTO/RPO、復元、障害、封じ込め、通知判断 | 12-01〜08 |
| 委託先・契約 | 審査、契約、再委託、SLA、終了時の処理 | 13-01〜08 |
| 人・端末・日常運用 | 個人別 ID、端末、入退社、教育、持出し | 14-01〜08 |
| AI・LLM・OCR | 送信データ、出力検証、権限、費用、回帰評価 | 15-01〜08 |

AI を使わないなら、その分野は理由を残して対象外にできます。単一企業向けのシステムなら、顧客間の分離は適用を判断します。ただし、利用者や部署の権限まで対象外にはしません。

### 最初に見る、公開前の確認表

全項目を評価する前に、重大な事故へつながる経路から確認します。以下は共通表から抜粋した入口です。

| 確認 | 合格条件の要点 | 証跡の例 | 詳細 ID |
| --- | --- | --- | --- |
| 管理者の認証 | 管理画面、クラウド、コード管理、CI/CD で MFA を強制する | MFA 未登録時の拒否結果 | 03-01 |
| 他人のデータ | ID を変えても他人・他部署・他顧客を参照、更新できない | 複数アカウントの否定テスト | 04-02 |
| 管理者機能 | 一般利用者が管理 API や全件出力を実行できない | ロール別の拒否結果 | 04-03 |
| 承認・確定 | 担当外の操作や段階飛ばしで確定できない | 状態遷移の試験 | 04-07 |
| 顧客間の分離 | DB 以外のキャッシュ、検索、ジョブでも境界を保つ | 顧客を切り替えた試験 | 05-02〜04 |
| 二重処理 | 並行実行や再送で二重承認、二重請求、二重計上を起こさない | 同時要求と再試行の試験 | 06-07 |
| Webhook | 不正署名を拒否し、同じイベントを重複処理しない | 改ざん・再送の試験 | 07-04〜05 |
| 秘密情報 | リポジトリ、配布物、ブラウザへ秘密キーを埋め込まない | 履歴と成果物のスキャン | 08-03 |
| 添付の保護 | 未認証や権限のない利用者へファイルを返さない | 直接 URL も含む取得試験 | 08-05 |
| 重大な脆弱性 | 実際の悪用状況と公開範囲を踏まえ、重大な未対処を残さない | 対応台帳と再検証 | 10-06 |
| 実際の復元 | 復元後に重要業務を実行できる | 復元時間と整合性の確認 | 12-04 |
| 事故の初動 | 封じ込め、証拠保全、連絡、通知判断の担当が決まっている | 連絡試験と机上演習 | 12-06〜07 |

この抜粋を全部通しても、評価完了ではありません。ここで大きな穴を見つけたら先に対処し、そのあと適用する残りの項目を確認します。

## ISMS の条件を足すと、見るものが増えた

最初に整理したのは、技術と運用の共通 120 項目でした。そのあとに加えたのが、「ISMS を取得している会社の要求を満たす」という条件です。

ここで必要になったのは、会社の文書とシステムの実態をつなぐ確認でした。

ISMS では、組織がリスクに応じて必要な水準を定めます。採用する管理策などは、適用宣言書に記録します。そのため、認証を取得しているという情報だけでは、個別システムの合格条件は決まりません。[ISMS-AC：ISMSとは](https://isms.jp/isms/)

**「会社が決めていること」と「このシステムで実施していること」を対応付けます。** そのための追加表が、ISMS-01〜20 です。

| 追加する確認 | 実際に照合するもの | 詳細 ID |
| --- | --- | --- |
| 認証・適用の範囲 | 認証書、対象業務、拠点、開発・運用・委託の境界 | ISMS-01〜02 |
| 会社の管理策・規程 | 適用宣言書の版、社内基準、具体的な設定値と試験 | ISMS-03〜04 |
| 資産・リスク・例外 | 台帳、リスク評価、対応計画、残余リスク、例外期限 | ISMS-05〜08 |
| 目標・外部委託・人 | 評価指標、委託先の承認、ID・端末・教育の適用 | ISMS-09〜11 |
| 変更・運用・復旧 | リリース、定期点検、事故報告、業務継続との整合 | ISMS-12〜15 |
| 証跡と文書 | 承認、版管理、閲覧権限、保存期間 | ISMS-16 |
| 監査と改善 | 内部監査、不適合の是正、経営層のレビュー | ISMS-17〜19 |
| 利用・提供の判断 | 社内の必須条件、未達事項、承認、認証表示の範囲 | ISMS-20 |

たとえば、社内規程にログの保存期間が書かれていたら、その期間を設定と運用記録に照合します。テンプレートの推奨値を入れた、という理由だけでは終わりません。

同じ理由で、共通表の P1 や P2 を見て、社内の必須事項を後回しにはできません。内部監査や経営層のレビューも、必要な工程として既存の ISMS に組み込みます。

新規システムでは、定期運用の実績がまだない場合があります。そのときは「計画は確認済み／運用実績は未確認」と記録します。予定を立てたことと、実施したことを混ぜないためです。

## 優先度と結果は、別々に記録する

優先度は、着手する順序や公開判断のために使います。P0・P1・P2 はこの表で定めた初期基準です。ISO や OWASP が一律にこの区分を指定しているわけではありません。

| 優先度 | 扱い |
| --- | --- |
| P0 | 公開・顧客データ投入前に確認する基本統制 |
| P1 | 原則として正式提供前に整える標準統制 |
| P2 | リスクと契約に応じて強化する統制 |

法令、契約、会社の ISMS で必要なら、その条件と期限を優先します。

一方、結果は次の 5 種類です。

| 結果 | 意味 |
| --- | --- |
| 適合 | 合格条件を満たし、有効な証跡がある |
| 一部適合 | 一部の機能・環境・条件だけ満たす |
| 不適合 | 合格条件を満たさない |
| 未評価 | 未確認、証跡なし、または証跡が古い |
| 対象外 | 構成や業務上、適用がない。理由と承認を残す |

適用する P0 に、不適合・一部適合・未評価が残る場合は公開可と判定しません。稼働中なら、影響と封じ込めを先に判断します。

例外を承認した場合も、結果を「適合」に変えません。残っている問題と、期限付きで運用する判断の両方を残します。

### 合格率が高くても、公開できるとは限らない

以下は説明用の例です。実システムの評価結果ではありません。

140 項目のうち、根拠のある対象外が 20 項目。適合が 110 項目で、残り 10 項目が未評価だったとします。

適合率は `110 ÷ (140 - 20) ≒ 91.7%` です。未評価も分母に含めます。

数字は悪く見えません。でも、その 10 項目に「他人の添付が読めないか」が残っていたら、公開判断は保留です。

**点数と一緒に、P0 の未達件数と未評価件数を出します。**

## 何を根拠に作ったのか

用途の違う基準を組み合わせました。以下は分野単位の参照関係です。個別管理策への正式な適合マッピングではありません。

| 基準 | 今回の使い方 |
| --- | --- |
| [NIST CSF 2.0](https://www.nist.gov/publications/nist-cybersecurity-framework-csf-20) | 統治、特定、防御、検知、対応、復旧を通して全体を見る |
| [ISO/IEC 27001:2022](https://www.iso.org/standard/27001) | 会社のリスク管理、管理策、運用、改善につなぐ |
| [OWASP ASVS 5.0.0](https://owasp.org/www-project-application-security-verification-standard/) | Web アプリの技術的な検証を具体化する |
| [OWASP API Security Top 10 2023](https://owasp.org/www-project-api-security/) | API 固有の主要リスクを補助点検する |
| [CSA CCM / CAIQ v4.1](https://cloudsecurityalliance.org/artifacts/cloud-controls-matrix-v4-1) | クラウドの責任分担と顧客への説明を整理する |
| [CIS Controls v8.1](https://www.cisecurity.org/controls/v8-1) | 資産、設定、端末、アクセスなどの運用を確認する |
| [NIST SSDF 1.1](https://csrc.nist.gov/pubs/sp/800/218/final) | 開発工程とソフトウェアの供給網を確認する |

参照の確認日は 2026 年 9 月 5 日です。詳細版には、認証やログなどの分野ごとの一次資料も載せています。

この 140 項目を埋めることと、ASVS L2 への適合を確認することは同じではありません。ASVS の適合を示す場合は、対象レベルの適用要件を別途すべて照合します。

国や業界の要求も追加します。たとえば、個人データの扱いやカード決済の適用範囲は、サービスごとの確認が必要です。詳しくは詳細版の「国・業界・契約で追加する確認」にまとめています。

## 使い始めるときの順番

最初から全項目を埋めようとするより、対象を決めて担当を分けたほうが進めやすいです。

1. **対象を決めます。** サービスの環境と版を記録し、扱うデータや顧客、外部連携を書きます。
2. **P0 から確認します。** 開発と運用で分担し、証跡を残します。
3. **ISMS の要求を照合します。** 認証範囲、適用宣言書、社内規程を確認します。
4. **残りの適用項目を評価します。** 未達には担当と期限を付けます。
5. **再検証して判断します。** 公開後は変更時と定期点検に組み込みます。

監査票のために証拠を集めるだけだと、更新されない表が増えます。設定変更、権限棚卸し、復元試験の記録を、同じ項目 ID へ紐付ける形にしています。

## 今回、表を作って整理できたこと

### 1. チェック項目には、合格条件が必要だった

「暗号化している」「認証がある」だけでは、評価者によってチェックの意味が変わります。確認方法と証跡を添えることで、次の担当者が同じ箇所を再検証できます。

**チェックを付ける根拠まで、表に含めます。**

### 2. ISMS の要求は、会社の文書から取り出す

共通の技術表だけでは、その会社が必要としている運用や承認を確認できません。追加 20 項目は、規程とシステムを照合するために設けました。

**適用宣言書と実際の証跡をつなげて、合格条件を確定します。**

### 3. 未評価を残せる表にする

作ったばかりの仕組みには、まだ運用実績がありません。そこで空欄を無理に埋めると、次に確認する人が困ります。

**未評価は消す対象ではなく、次に確認する作業として管理します。**

## おわりに

今回公開したのは、開発担当と運用担当、ISMS 担当が一緒に使うための初期版です。これから会社ごとの規程やサービスのリスクに合わせて育てていく前提で作りました。

まずは自分のシステムを 1 つ選び、P0 の行に証跡を付けてみてください。実装を読む作業、設定を確かめる作業、会社に確認する作業が分かれてきます。
