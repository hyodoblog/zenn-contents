# はじめに

エンジニア人生には、何度か「画面を見た瞬間に脳がフリーズする」イベントが用意されています。私の番が回ってきたとき、画面にはこう表示されていました。

**Google Cloud 請求額：1000 万円超。**

しかも笑えないのが、この 1000 万円を叩き出した犯人が **「バグを早く見つけるために、自分で作った監視の仕組み」** だったこと。バグを狩るために放ったはずのハンターが、いつのまにか自分自身を食い散らかし、請求書という名の怪獣に育っていたわけです。マッチポンプにもほどがある。

この記事は、その一部始終の記録です。なぜ気づけなかったのか、どう出血を止めたのか、いくら戻ってきたのか、そして二度と味わわないために何をしたのか。クラウドを本番で回している人にとっては、明日は我が身の話だと思います。どうぞ、他人事のような顔で読んでください（フラグ）。

# 事象

発生時期は 2023 年 8 月 22 日から 9 月 2 日。たった 10 日ほどで、桁がひとつどころか複数ズレた請求が静かに積み上がっていきました。

こちらが実際の請求ダッシュボードです。途中まで平和なグラフが、ある地点から急に **エベレストの断面図** みたいになっているのが分かると思います。

ちなみにこのまま気づかず放置していた場合、着地見込みは **月あたり約 4600 万円**。都内にいい感じの一軒家が建ちます。ログで。

# ストーリー

## 発端：2週間、通知が鳴かなかった

当時、とある LINE ミニアプリの案件を担当していました。バグ報告は一秒でも早く察知したい。そこで **Cloud Run や Cloud Functions でエラーログが流れたら、即 Discord に通知が飛ぶ** 仕組みを自作していました。我ながら良い仕事です。3 ヶ月、何の問題もなく動いていました。

ところがある時期、**通知がぱったり止みました。2 週間、無音。**

正直、一瞬こう思いました。

> 「……ついに、バグのないサービスが完成したのでは？」

いや、そんなわけがない。3 ヶ月動いたコードが突然“無”になるはずがない。嫌な予感を押し殺しながら、サービスのログを手動で見に行きました。

そこで私を待っていたのが、**1000 万円を超えた月額請求** です。

> 「？？？？」

脳が処理を放棄し、数分間フリーズ。恐る恐るお支払いログを開くと、そこには無情の三文字。**「支払い済み」**。

ここで私は **無量空処** をくらいました。無限の情報が一度に流れ込み、思考が停止する、あの技です。たまらずノートPCをそっと閉じ、10 分ほど散歩に出ました。夏の風が心地よかったです（現実逃避）。

戻ってきた私は、深呼吸をひとつして、ようやく原因探しを始めました。

## 原因：番人が、自分を殴り続けていた

調べてわかった費用の正体は、**大量のログ出力によるストレージ課金** でした。

どのくらい大量かというと、**1 ミリ秒あたり数百〜数千行**。1 秒に換算すると約数万行。それが延々と続いていました。しかも中身は全部同じエラー。同じ悲鳴を、マシンガンで、無限に、撃ち続けていたわけです。

つまり——

> **エラーを検知する仕組みが、エラーを起こしていた。**

バグを見張るはずの番人が、自分のエラーで発狂し、その悲鳴でまた自分を殴り、その痛みでまた叫ぶ。完全な自家中毒。永久機関を作るなら請求書ではなくノーベル賞で作ってほしかった。

とにかく延焼を止めるのが先決なので、エラー検知に使っていた **Cloud Functions と Pub/Sub をまるごと削除**。これで課金の蛇口を閉じました。放置していれば月 4600 万円コースだったので、この一手でだいぶ命拾いしました。

## クライアントへの連絡：日曜ランチタイムの緊急 Zoom

原因を完全に突き止めるより前に、まずはクライアントへ第一報を入れました。事故は、隠すほど傷が深くなるやつです。

タイミングはあいにくの日曜ランチどき。返信は約 1 時間後でした。幸い、その頃には原因特定と一次対応（該当リソースの削除）まで終わっていたので、急遽 Zoom をつなぎ、「何が起きたか・原因・すでに打った手」を順に共有。**発覚から報告までを一気に駆け抜けられた** ことが、のちの信頼につながったと思います。ランチを中断させてしまったのは、本当に申し訳なかったですが。

## Google Cloud への問い合わせ：証拠を握りしめて

費用の発生箇所は特定できました。が、最大の謎が残っていました。**そもそも、なぜログがここまで爆発したのか？**

ログを見る限り、Pub/Sub 側でエラーが起きており、その先で動くはずの Functions は実行されていません。Functions が動いてエラーになっているなら、こちらのコードを直せば済む話。ところが今回は Pub/Sub 側のエラーが延々とログに吐かれ続けており、自分の実装だけでは説明のつかない挙動でした。

そこで、この件を Google Cloud に問い合わせることにしました。武器は感情ではなく証拠です。発生時期の請求データと、暴走していたログのスクリーンショットを添え、**「エラー検知の仕組みが、自分自身のエラーで短時間に膨大なログを生成し、想定外の費用が発生した」** という経緯を、時系列で淡々と説明しました。「返金してくれ！」と叫ぶのではなく、事実を積み上げて相手に判断してもらう。ここは冷静さが命でした（散歩の効果）。

## 結末：まさかの全額返金

結論から言います。

**——全額、返ってきました。**

サポートとのやり取りを経て、今回のケースが「意図的な利用ではなく、想定外の挙動による異常な課金」と認められ、最終的にクレジットという形で全額が戻ってきました。あの日、PCを閉じて夏の道を歩いていた自分に「大丈夫、最後は無罪放免だ」と教えてあげたい。

ただし——ここで「返金されたしヨシ！」と現場猫になって終わってはいけません。**返金は救済であって、保証ではない。** タイミングや状況が違えば、そのまま数千万円の負債を抱えていた世界線も普通にありました。というわけで、ここからが本当の本題。再発防止です。

# 対策

同じ怪獣を二度と孵化させないため、大きく 2 つの手を打ちました。

## 1. 予算アラート・請求通知の設定

今回いちばんの敗因は、**1000 万円に到達するまで、誰も気づけなかった** ことに尽きます。逆に言えば、早い段階で通知さえ鳴っていれば、被害は数百円〜数千円で終わっていたはず。1000 万か、数百円か。天国と地獄の差は「通知」だけでした。

そこで Cloud Billing の **予算（Budget）とアラート** を設定。月額の想定コストに対して 50% / 90% / 100% の閾値を超えたら、即メール・Discord に通知が飛ぶようにしました。

「請求は毎月ちゃんと目視で確認する」なんて運用ルールは、忙しくなった瞬間に蒸発します。**人間の意志力に頼らず、閾値を超えたら機械に叫ばせる。** これが最強にして最安の保険です。

## 2. エラー通知の再設計（マッチポンプを止める）

今回の事故の本質は、**「監視する仕組み自身が壊れたとき、それを止める人がいなかった」** ことでした。エラーを検知して通知する経路（Functions / Pub/Sub / Discord）が、自分のエラーで自分に燃料をくべ続ける、完全なマッチポンプになっていたのです。

そこで通知パイプラインを次の方針で作り直しました。

- **同一エラーの集約とレート制限**：同じエラーは一定時間ぶんをまとめて 1 通に。1 ミリ秒に数千行、みたいな地獄を物理的に発生させない。
- **通知経路自身のエラーはループさせない**：通知の仕組みがコケたとき、その失敗をまた同じ通知経路に流し込まない。自己参照の輪を、ハサミで断ち切る。
- **「通知が来ない＝正常」と思い込まない**：ハートビート的に「元気に生きてます」の生存確認も定期送信。静寂を “平和” ではなく “異常のサイン” として疑えるようにする。

# 学び

高すぎる授業料（一時 1000 万円）で買った教訓です。

- **監視する仕組みも、監視の対象である。** 「監視の監視」がないと、番人が倒れても誰も気づけません。番人にも見張りを。
- **「通知が来ない＝バグがない」ではない。** 沈黙は平和ではなく、最も危険なサインになり得ます。「バグのないサービスができた」と喜びかけたあの瞬間こそ、地雷の真上でした。
- **予算アラートは “いつか” ではなく “いま” 設定するもの。** クラウドは、コードのバグがそのまま青天井の請求に直結する世界。上限と通知は、本番リリースより前に置いておくべきインフラです。
- **異常を見たら、まず出血を止める。** 完全な原因究明より先に、金を燃やしている Functions と Pub/Sub を切り離した初動は正解でした。
- **クライアントとプロバイダには、早く・事実ベースで。** 隠さず、証拠を添えて、冷静に。これがクライアントの信頼維持と全額返金、両方の決め手でした。

# まとめ

「バグを早く見つけたい」という善意から生まれた仕組みが、月 1000 万円（放置なら月 4600 万円）の怪獣に育ち、最後は全額返金で幕を閉じる——。ジェットコースターにもほどがある 10 日間でした。

クラウドの本番運用では、**コードの正しさと同じくらい、「壊れ方」と「気づき方」を設計しておくこと** が大事だと、身をもって学びました。この記事が、同じ無量空処を味わう人をひとりでも減らせたら本望です。

……というわけで、この記事を閉じたら、まず予算アラートを設定しに行きましょう。今すぐです。マジで。
