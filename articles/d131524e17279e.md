同じ会員が使うアプリが 3 つになりました。どのアプリも「この人は会員か」を判定する必要があります。素直に作ると、判定が 3 か所に散ります。私は最初、共通の関数を配れば済むと考えていました。散ったあとで会員の定義が変わると、3 か所とも直すことになります。

そこで認証だけを別アプリへ切り出し、Better Auth の `@better-auth/oauth-provider` で自前の IdP を立てました。結論から言うと、OIDC の口を生やすところは設定で終わります。効いたのはそこではなく、**認証の経路を 1 本に絞ったことと、会員判定をセッションが作られる前へ置いたこと**でした。

同じようにアプリが増えて認証を集約しようとしている人の時短になれば嬉しいです。この記事は 3 本目です。1 本目と 2 本目はこちらです。

https://zenn.dev/yoshinani_dev/articles/3306277f57fd1c

https://zenn.dev/yoshinani_dev/articles/762690f92d33f8

:::message
受託で運用している業務システムの実装をもとにしています。クライアント名・プロダクト名・ドメイン・会員種別などの業務固有の用語は伏せ、一般的な名前に置き換えています。クライアント ID などの識別子は載せていません。
:::

## アプリが 2 つになった時点で崩れたもの

前の記事では、1 つのアプリの中で組織とロールを扱いました。アプリが増えると、前提が変わります。

| 増えたときに困ること | 1 アプリなら | 3 アプリだと |
| --- | --- | --- |
| 会員かどうかの判定 | 1 か所 | 3 か所に散る |
| 会員の定義変更 | 1 か所直す | 3 か所直す。ずれる |
| ログイン状態 | そのアプリだけ | アプリごとに入り直す |
| 退会した人の締め出し | すぐ効く | 反映が遅いアプリが出る |

> それぞれのアプリで同じ関数を呼べば済む話だと思っていました。

済みませんでした。同じ関数を呼んでも、呼び忘れたアプリが 1 つあれば終わりです。**判定を共有するのではなく、判定を通っていない人にはセッションを渡さない**ほうが確実でした。

## つくったもの

- **IdP**: Next.js（App Router）+ Better Auth + `@better-auth/oauth-provider`
- **ログイン方法**: LINE ログインのみ
- **会員台帳**: 外部の台帳サービスを参照（LINE ユーザー ID で引く）
- **RP**: 自社の 2 アプリ。あとから増える前提

IdP 側は OIDC の口を 2 つ生やします。プラグインを入れるとメタデータは自動で組み立てられます。

```ts:app/.well-known/openid-configuration/route.ts
import { oauthProviderOpenIdConfigMetadata } from "@better-auth/oauth-provider"

const handler = oauthProviderOpenIdConfigMetadata(auth)
```

ここは設定です。難しいのは、この先にありました。

## 認証経路を 1 本に絞る

まずメールとパスワードでのログインを、明示的に切りました。

```ts:auth.ts
// 会員判定は LINE ユーザー ID を台帳へ照会して行う。
// 並行する資格情報の経路を残すと、非会員がその検査を迂回できる。
emailAndPassword: {
  enabled: false,
},
socialProviders: {
  line: { clientId: ..., clientSecret: ... },
},
```

**会員判定の入力が LINE ユーザー ID なので、LINE を通らない経路があると判定できません。** パスワードで入れるようにした瞬間、LINE ユーザー ID を持たないアカウントが生まれます。そのアカウントを台帳で引くと、当然どの会員にも一致しません。

ここで「一致しなければ拒否」にすれば安全に見えます。実際は逆で、**判定できない人を作らないほうが安全**でした。拒否の分岐は、書き忘れれば通ってしまいます。経路が 1 本なら、書き忘れる場所がありません。

——**塞ぐ分岐を増やすより、分岐そのものを減らすほうが確実です。**

## 会員判定は、セッションが作られる前に置く

判定をどこへ置くかで、作れてしまう状態が変わります。置いたのは、セッションが作られる直前です。

```ts:auth.ts
databaseHooks: {
  session: {
    create: {
      before: async (session) => {
        const lineAccount = await client.account.findFirst({
          where: { userId: session.userId, providerId: "line" },
          select: { accountId: true },
        })
        if (!lineAccount) {
          throw new APIError("FORBIDDEN", { message: NOT_MEMBER_MESSAGE })
        }

        const membership = await lookupMembership({
          lineUserId: lineAccount.accountId,
        })
        if (membership.status !== "active") {
          throw new APIError("FORBIDDEN", { message: NOT_MEMBER_MESSAGE })
        }
      },
    },
  },
},
```

ここで落とすと、**セッションのクッキーが発行される前に止まります**。画面側で「ログインはできたが会員ではない」という状態を扱わなくて済みます。

この状態を作ってしまうと、あとが面倒です。ログイン済みの人をどの画面まで通すか、どこでサインアウトさせるか、戻り先はどこか。分岐が増えて、そのどれかを落とします。**存在しない状態は、扱う必要がありません。**

## LINE はメールを返さない

素直に組むと、ここで止まります。LINE はユーザーがメールを共有していない場合、あるいはチャネルがメールの利用申請をしていない場合、メールを返しません。一方で Better Auth の User はメールを必須にしています。

> 会員判定に使っていないのだから、空でも通るはずでした。

通りませんでした。スキーマが必須にしている以上、何かを入れる必要があります。置き場所を用意しました。

```ts:auth.ts
mapProfileToUser: (profile: { sub?: string; email?: string }) => ({
  email: profile.email || `${profile.sub || "unknown"}@line.placeholder`,
  emailVerified: !!profile.email,
}),
```

**プレースホルダーを入れるうえで大事なのは、`emailVerified` を嘘にしないことです。** ここを一律 `true` にすると、あとからメールを使う機能を足したときに、届かないアドレスへ送り始めます。会員判定は LINE ユーザー ID で行っているので、メールは識別子として使っていません。

## IdP は「閉じない口」を持つ

1 本目と 2 本目では、全部閉じる方向で書きました。IdP は違います。**OIDC のメタデータは、RP から認証なしで読めなければ動きません。**

```ts:proxy.ts
export const config: ProxyConfig = {
  matcher: [
    {
      source:
        "/((?!_next/static|_next/image|favicon.ico|.well-known/|api/|images/|auth/|public/).*)",
    },
  ],
}
```

`.well-known/` を除外しています。1 本目で「定型の除外パターンを貼るな」と書きましたが、ここでは**除外する理由がはっきりしています**。仕様上、公開が要求されている口だからです。

除外パターンは、貼るかどうかではなく、1 行ごとに理由を言えるかどうかで判断します。理由を言えない行が混ざっていたら、そこが穴です。

## 同じ社内で、逆の判断をしている場所がある

2 本目で「環境変数が無いまま起動しない」と書きました。招待リンクの土台が未設定だと、開けない URL をメールで配るからです。

同じ会社の IdP 側は、逆の判断をしていました。

```ts:auth.ts
// Resend は招待メール送信時にしか使わないので遅延初期化する。
// モジュール読み込み時に throw すると、環境変数が一部欠ける
// プレビュー環境で静的ページの収集が落ちるため。
let _resend: Resend | null = null
const getResend = (): Resend => {
  if (_resend) return _resend
  const key = process.env.RESEND_API_KEY
  if (!key) throw new Error("RESEND_API_KEY is not set")
  _resend = new Resend(key)
  return _resend
}
```

片方は起動時に落とし、片方は使うときまで遅らせます。**どちらが正しいかではなく、何を守りたいかが違います。**

| | 起動時に落とす | 使うときまで遅らせる |
| --- | --- | --- |
| 守るもの | 壊れた状態で動き続けないこと | 環境変数が揃わない環境でもビルドが通ること |
| 向く対象 | 認証など、無いと成立しない設定 | メールなど、一部の経路でしか使わない設定 |
| 事故り方 | プレビューのビルドが落ちる | 送信のときに初めて気付く |

前の記事で「設定漏れは閉じる側へ倒す」と書いたのは、**認証の話だから**でした。全部を起動時に落とすと、プレビュー環境が動かなくなります。**倒す方向は、その設定が無いと何が壊れるかで決めます。**

## ID トークンに状態を載せると、どこまで遅れるか

RP 側が毎回 IdP へ会員かどうか聞きに行くのは無駄です。ID トークンへ載せました。

```ts:auth.ts
customIdTokenClaims: async ({ user }) => {
  const membership = await lookupMembership({ ... })
  return {
    community_status: membership.status,
    course: membership.course,
  }
},
```

これは 2 本目で書いたセッションキャッシュと同じ論点を持ちます。**載せた瞬間から、その値はトークンの有効期間だけ古くなりえます。**

退会した人がその日のうちに締め出される必要があるなら、トークンの有効期間を短くするか、重要な操作の前に台帳を引き直します。「トークンに書いてあるから会員」で通してよい操作と、そうでない操作を分けておきます。

あわせて、自社の RP は同意画面を飛ばしています。

```ts:auth.ts
// 自社の RP。同意画面を飛ばす。新しい RP が増えたら更新する
cachedTrustedClients: new Set([ /* client id */ ]),
storeClientSecret: "hashed",
storeTokens: "hashed",
```

クライアント ID をコードへ書く形なので、**RP が増えたときにここを直し忘れると、自社アプリなのに同意画面が出ます**。壊れ方としては軽いほうですが、更新箇所が分散する種類の設定だと覚えておきます。クライアントシークレットとトークンは、保存時にハッシュ化しています。

## チェックリスト

IdP を立てるときに決めることを、項目へ落としました。公開範囲や認可まで含む全 66 項目は、[GitHub の詳細版](https://github.com/hyodoblog/zenn-contents/blob/main/docs/internal-app-checklist/checklist.md)にあります。

- [ ] 認証経路を 1 本に絞り、判定できないアカウントが生まれない状態にした
- [ ] 会員判定を、セッションが作られる前に置いた
- [ ] 「ログイン済みだが会員ではない」状態を、そもそも作らない設計にした
- [ ] 外部プロバイダーがメールを返さない場合の扱いを決めた
- [ ] `emailVerified` に嘘を入れていない
- [ ] proxy の除外パターンが、1 行ごとに理由を言える
- [ ] 環境変数を倒す方向を、その設定が無いと何が壊れるかで決めた
- [ ] ID トークンへ載せた状態が、どれだけ古くなりうるか把握した
- [ ] トークンの値で通してよい操作と、引き直す操作を分けた
- [ ] RP を追加したとき、更新が必要な箇所を書き出した
- [ ] クライアントシークレットとトークンをハッシュ化して保存している

## 学び

### 1. 分岐を塞ぐより、分岐を作らない

パスワード認証を残して「非会員なら拒否」と書くこともできました。書き忘れれば通ります。経路を 1 本にすると、書き忘れる場所が消えます。**拒否の実装が正しいかを検査し続けるより、拒否が要らない形にするほうが安上がりです。**

### 2. 存在しない状態は、扱わなくてよい

セッションを作る前に落とすと、「ログイン済みの非会員」という状態が生まれません。生まれない状態のために画面を作る必要も、テストを書く必要もありません。**設計で状態を減らすと、実装より先にテストが減ります。**

### 3. 除外パターンは、1 行ずつ理由を言えるか

`.well-known/` を外すのは仕様上の要求です。`api/` を外すのは、防御線を下に置いたからです。理由を言えない行だけが危険です。**定型が悪いのではなく、理由の無い定型が悪いです。**

### 4. 倒す方向は、壊れるものによって変える

認証は起動時に落とす。メールは使うときまで遅らせる。同じ「環境変数の設定漏れ」でも、無いと何が壊れるかが違えば、倒す方向も違います。**フェイルセーフは方針ではなく、対象ごとの判断です。**

## おわりに

IdP を立てる作業そのものは、プラグインを足してメタデータの口を生やすだけでした。時間を使ったのは、認証の経路を減らすところと、判定をどこへ置くかを決めるところです。

アプリが 3 つになると、正しく書くことより、間違えられる場所を減らすことのほうが効きます。3 か所に同じ判定を書いて 3 か所とも正しく保つより、判定を通っていない人にセッションを渡さないほうが、確実で短いです。
