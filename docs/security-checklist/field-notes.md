# 公開済みの事例とチェック項目の対応

対象：チェックリスト公開版1.1 ／ 確認日：2026-09-05

過去の記事に記載された事実と、今回のチェックリストで求める確認を分けて整理しています。元の記事で行っていない検証を、実施済みと扱うものではありません。個別案件の現在の安全性を評価した資料でもありません。

## 1. 一括承認で一部の検査が抜けていた

出典：[管理画面を作るのはもうやめる。業務ツールは MCP 起点で十分だった](https://zenn.dev/yoshinani_dev/articles/a4c592b2b23ed7)

**過去記事の事実：** 個別承認では実施していた送信抑止・送信根拠の鮮度の検査が、一括承認では抜けていました。状態遷移とガードをサービス層へ集約し、各入口から共通処理を呼ぶ構成へ変更しています。

**今回の反映：** 04-01でUI、API、MCP、一括操作、バッチの入口を列挙し、同じ拒否対象を各経路で試します。04-07の承認順序、11-02の操作主体・操作経路の追跡にも関係します。

**今回補足した点：** 元の記事には`confirmed: true`という入力例があります。この値だけでは、人が承認した証明にはなりません。15-06では、承認者・対象・内容をサーバー側の記録と結び付け、実行時に照合する条件を具体化しました。宛先や金額の変更、期限切れ、再利用を試験します。モデル自身が作れるフラグや記録を、人の承認として受け入れない設計が必要です。

技術的な参照：[OWASP Transaction Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html)、[OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

## 2. 監視通知の停止とログ課金

出典：[Google Cloud請求額が1000万円を超えた話](https://zenn.dev/yoshinani_dev/articles/f30274290511a1)

**過去記事の事実：** エラーの通知が停止し、大量のログ出力による課金が発生した経緯が記録されています。記事では通知の集約・レート制限、通知自身のエラーのループ抑止、生存確認、予算通知を対策として挙げています。

**今回の反映：** 11-08に、通知先停止時の別経路への到達と通知ループの抑止を追加しました。07-06では、外部API等の高額処理について、費用の通知と処理の制限を分けて確認します。AIを利用する場合は15-07の実行回数・費用制限も評価します。

**確認する試験：** 通知先停止、同一エラーの連発、通知処理自身の失敗、ハートビート欠損を模擬します。通知・ログの量が制御され、別の連絡先へ届くことを確認します。停止手段には担当者、停止対象、再開条件を設定します。

**今回補足した点：** Google Cloudの通知のみの予算設定は、それだけで利用額を制限しません。費用上限の機能を採用する場合も、対象サービス・適用範囲・遅延・業務影響を個別に確認します。過去記事の返金という結果を、将来の救済や安全性の根拠にしません。

技術的な参照：[Cloud Billing：予算と通知](https://docs.cloud.google.com/billing/docs/how-to/budgets)。

## 3. 複数のCheckout URLからの二重決済

出典：[【Stripe】有効なCheckout URLを複数発行しないための施策【二重決済対策】](https://zenn.dev/yoshinani_dev/articles/bd996b5737b5b5)

**過去記事の事実：** 複数の決済URLを別端末・別タブで開いて決済する事象と、既存の有効URLを失効させる対策が紹介されています。

**今回の反映：** 06-07で、同じ要求の再試行と、同じ注文に対して別々の要求が並行する場合を区別します。再送時の冪等キーだけでなく、注文・確定状態の一意性や状態遷移を試験します。

**確認する試験：** 別タブ・別端末からの同時生成、別の要求IDを使った同一注文の操作、決済成功後に応答だけが失われた場合、Webhookの重複・順序逆転を再現します。注文側の記録と決済側の結果を照合します。

**今回補足した点：** 既存URLの一覧取得・失効・新規作成だけでは、同時実行に対する一意性を保証しません。Stripeの冪等キーは同じ要求の再試行を扱う仕組みであり、異なるキーによる別要求を業務上の同一注文として統合しません。元の記事のコードだけで二重決済を完全に防げる、とは判定しません。

技術的な参照：[Stripe：Idempotent requests](https://docs.stripe.com/api/idempotent_requests)。

## 4. キャッシュを無効化する更新経路の見落とし

出典：[同じSupabaseなのに管理画面が遅い。犯人はクエリではなく取りに行く場所だった](https://zenn.dev/yoshinani_dev/articles/3f9a1c7e08b24d)

**過去記事の事実：** 更新処理を調査した結果、別機能のCSV取込みがマスタを書き換える経路が見つかりました。署名付きURLの期限を考慮し、データのキャッシュとURL発行を分けた設計も記録されています。

**今回の反映：** 05-03で、画面以外の更新経路、顧客切替、権限変更後のキャッシュを確認します。08-05では、署名付きURLと認可付き配信を区別し、発行後に権限を削除した場合の取得可能時間を確認します。

**確認する試験：** 画面・CSV・バッチ・外部連携から更新し、キャッシュ命中時も必要な整合性が維持されるか試します。別テナントの同一キー、権限削除後のセッション、発行済みURL、ブラウザー／CDNのキャッシュを確認します。

**今回補足した点：** 元の記事で実際の越境漏えいを観測したという意味ではありません。今回の権限変更・失効試験は、その設計上の注意をセキュリティ評価へ広げたものです。署名付きURLを一律にキャッシュ禁止とはせず、期限と許容失効時間から方式を選びます。すでにダウンロードされたファイルを権限削除で回収できるとは扱いません。

技術的な参照：[OWASP Multi-Tenant Security](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)、[OWASP Authorization](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)。

## 5. 本番ビルドでlockfileが無視された

出典：[bun へ移行したら本番だけパッケージが倍に増えた。ロックファイルが黙って無視されていた](https://zenn.dev/yoshinani_dev/articles/b66uxw1wbwf554)

**過去記事の事実：** 本番ビルドでlockfileの形式を読めず、警告後に依存を再解決したログが記録されています。固定lockfileでの導入を指定した後は、不一致でビルドが停止しています。

**今回の反映：** 10-05で、設定ファイルの指定だけでなくCIログの実ツール版と実際の固定状態を確認します。開発環境とCIの差分を追跡し、不一致で停止することを試験します。

**確認する試験：** 本番相当の隔離環境でmanifestとlockfileを不一致にし、別の依存を黙って入れずに停止するか確認します。通常時はlockfile、部品一覧、成果物の来歴を対応付けます。

**今回補足した点：** 当時のツール挙動を、現在のすべてのバージョンに一般化しません。固定lockfileは安全な部品を保証する機能ではないため、脆弱性検査と供給元の確認も継続します。

技術的な参照：[pnpm install --frozen-lockfile](https://pnpm.io/cli/install#--frozen-lockfile)、[NIST SSDF](https://csrc.nist.gov/pubs/sp/800/218/final)。
