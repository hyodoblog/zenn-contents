# 社内アプリ公開・認証チェックリスト：詳細版

公開版：1.0 ／ 作成・参照確認日：2026-09-09 ／ 言語：日本語

**目的：社内向けのWebアプリをVercel等へ公開するとき、公開範囲・認証・認可・秘密情報の設定漏れを、実装前と本番反映後の2時点で機械的に確認する。**

対象は、社内の限られた人だけが使うWebアプリ。ヘッドレスCMSや業務データを載せ、URLを知られた時点で困る種類の情報を扱うものを想定する。個別システムの監査結果ではなく、初期状態は全項目「未確認」。

このチェックリストの根拠となった実例は、以下の記事に記録している。

- [Claude CodeやCodexで社内アプリを作るときの注意点](https://zenn.dev/yoshinani_dev/articles/3306277f57fd1c)
- [Better Authの組織プラグインで社内アプリの認証を作った](https://zenn.dev/yoshinani_dev/articles/762690f92d33f8)
- [アプリが3つになったので自前のIdPを立てた](https://zenn.dev/yoshinani_dev/articles/d131524e17279e)

より広い範囲の一般的な項目は、[システムセキュリティチェックリスト](../security-checklist/checklist.md)を参照する。本書はそれを社内アプリの公開範囲と認証に絞って具体化したもの。

## 1. エージェントに渡す文脈

AIエージェントがコードを書く前提で、リポジトリに書いていない前提は存在しない前提として扱う。

| # | 確認項目 | 確認方法 |
| --- | --- | --- |
| 1-01 | `CLAUDE.md` または `AGENTS.md` にアプリの公開範囲が書かれている | `ls CLAUDE.md AGENTS.md` |
| 1-02 | 「社内向け」「認証が必要」「本番に載る情報の種類」が明文化されている | 該当ファイルを読む |
| 1-03 | READMEの記述が公開範囲と矛盾していない | `grep -niE "社内|公開|非公開|認証" README.md` |
| 1-04 | SEO対策とアクセス制御を、別のタスクとして依頼している | 依頼文とコミットメッセージを読む |
| 1-05 | フレームワークのメジャーバージョンを指示に明記している | 依頼文を読む |
| 1-06 | 参照させたドキュメントが公式かつ最新である | 一次情報のURLを確認する |
| 1-07 | 雛形から起こした他リポジトリにも同じ確認を適用した | テンプレート由来のリポジトリを列挙する |

## 2. 公開範囲

Vercelは1つのデプロイに複数のURLを配る。すべて確認する。

| # | 確認項目 | 確認方法 |
| --- | --- | --- |
| 2-01 | 本番のカスタムドメインが、認証なしで200を返さない | `curl -s -o /dev/null -w "%{http_code}\n" https://<domain>/` |
| 2-02 | 本番の生成URLでも同じ結果になる | `<project>-<scope>.vercel.app` を叩く |
| 2-03 | ブランチURLでも同じ結果になる | `<project>-git-<branch>-<scope>.vercel.app` を叩く |
| 2-04 | 叩いたURLが本当に自分のサイトである | `curl -s <url> \| grep -o "<title>[^<]*</title>"` |
| 2-05 | Deployment Protectionの**範囲**を確認した | Standard Protectionは本番ドメインを守らない |
| 2-06 | プラン上、本番ドメインを閉じられるか把握した | Hobbyでは閉じられない。アプリ側で塞ぐ |
| 2-07 | プロジェクト名とチーム名からURLが推測できる前提で考えた | 命名を外部から当てられるか検討する |
| 2-08 | 静的ファイルと `public/` の画像にも認証がかかる | 画像URLを直接叩く |
| 2-09 | 過去の本番デプロイが残っていないか確認した | 保持期間と保護範囲を確認する |

## 3. 認証：入口を閉める

| # | 確認項目 | 確認方法 |
| --- | --- | --- |
| 3-01 | 認証をかける層を決めている | Deployment Protectionか、アプリのproxyか |
| 3-02 | `matcher` の除外パターンが、決めた層と矛盾していない | proxyが防御線なら `api` を除外しない |
| 3-03 | 環境変数が未設定のとき、本番が閉じる側へ倒れる | 変数を外して本番相当で起動し、応答を見る |
| 3-04 | 空文字が「設定済み」と扱われない | `emptyStringAsUndefined` 等を有効にする |
| 3-05 | Basic認証のパスワードが辞書語でない | 生成した値を使う |
| 3-06 | パスワードの共有範囲と、退職時に変える手順が決まっている | 運用手順書を確認する |
| 3-07 | 認証情報がリポジトリに入っていない | `git ls-files` と履歴を確認する |

## 4. 認可：誰が何をしてよいか

Basic認証では扱えない領域。ロールを分ける段階で確認する。

| # | 確認項目 | 確認方法 |
| --- | --- | --- |
| 4-01 | 組織のユーザー新規作成と削除を止めている | `allowUserToCreateOrganization` / `disableOrganizationDeletion` |
| 4-02 | 最後の管理者が消えない | `creatorRole` を管理者にする |
| 4-03 | ロールの数が、運用できる数まで絞られている | ロール定義を読む |
| 4-04 | サインアップを閉じ、入口を招待だけにしている | 認証設定を読む |
| 4-05 | メール認証を飛ばす判断が、招待制であることとセットになっている | 該当フックを読む |
| 4-06 | proxyを防御線にしているか、前捌きかを決めている | 実装のコメントで明示する |
| 4-07 | 前捌きなら、画面・Server Action・Route Handlerのそれぞれにガードがある | 各入口を列挙して確認する |
| 4-08 | Server Actionで、引数のIDがその組織のものか確かめている | ガード実装を読む |
| 4-09 | 他組織のリソースを403ではなく404にしている | 存在を開示しない |
| 4-10 | セッションをクッキーの有無ではなく実体で検証している | `getSession` を通しているか確認する |

## 5. ライブラリの標準API

認証ライブラリが自動で生やすエンドポイントは、要件より緩いことがある。

| # | 確認項目 | 確認方法 |
| --- | --- | --- |
| 5-01 | ブラウザーへ公開するエンドポイントを許可リストにしている | 拒否リストはバージョンアップで穴が開く |
| 5-02 | 他人のロールを引ける標準APIを塞いでいる | `get-active-member-role` の `userId` 付き呼び出し |
| 5-03 | メンバー一覧を誰が引けるか決めている | `listMembers` の到達性を確認する |
| 5-04 | バージョンを上げたとき、増えたエンドポイントが既定で拒否される | 許可リストの実装を読む |
| 5-05 | パスのパーセントエンコードで許可リストを迂回できない | エンコードした経路で叩く |
| 5-06 | 標準APIの権限判定を、ドキュメントではなく実装で確認した | `node_modules` の該当ファイルを読む |

## 6. 秘密情報

| # | 確認項目 | 確認方法 |
| --- | --- | --- |
| 6-01 | `.env` 系のファイルがGitに入っていない | `git ls-files \| grep env` |
| 6-02 | 過去のコミットにもAPIキーが残っていない | 履歴を検索する |
| 6-03 | クライアントに出す値を `NEXT_PUBLIC_` に入れていない | 変数名を列挙する |
| 6-04 | 本番のDBへ開発環境から直接つながる設定になっていない | 接続先を確認する |
| 6-05 | `trustedOrigins` に入れた生成URLが保護されている | 該当URLを叩く |

## 7. 検索エンジン

認証で閉じたなら保険。閉じていないなら、これは鍵ではない。

| # | 確認項目 | 確認方法 |
| --- | --- | --- |
| 7-01 | `robots.txt` の `Disallow` とnoindexの意味を分けて選んでいる | 併用するとnoindexが読まれない |
| 7-02 | 認証で閉じたうえで、検索対策を保険として位置付けている | 設計意図を記録する |
| 7-03 | プレビューに付く `x-robots-tag` が本番には付かないと理解している | `curl -sI` で確認する |
| 7-04 | カスタムドメインを付けた時点で、証明書の記録から名前が分かることを許容した | 公開範囲の判断に含める |

## 8. 運用

| # | 確認項目 | 確認方法 |
| --- | --- | --- |
| 8-01 | 環境変数を入れただけで終わらせず、コードをデプロイして再度叩いた | マージ後に再測定する |
| 8-02 | 本番反映後、もう一度ステータスコードを測った | 反映前の測定は反映後の証拠にならない |
| 8-03 | メール送信の失敗が、ログではなく追える場所に残る | 送信結果の戻り値を捨てていないか確認する |
| 8-04 | セッションキャッシュの分だけ何の反映が遅れるか把握した | 除名と失効を分けて考える |
| 8-05 | 退職者を外す操作が、遅延なく効く | 所属をDBで引いているか確認する |
| 8-06 | 半年後に同じ確認をする担当と時期が決まっている | 定期点検の予定を作る |

## 9. 複数アプリを1つのIdPへ集約する

アプリが増えて認証を切り出す段階で確認する。

| # | 確認項目 | 確認方法 |
| --- | --- | --- |
| 9-01 | 認証経路が1本に絞られ、判定できないアカウントが生まれない | 有効なプロバイダーを列挙する |
| 9-02 | 会員判定をセッション生成前に置いている | `databaseHooks.session.create.before` 等 |
| 9-03 | 「ログイン済みだが会員ではない」状態が発生しない | 落ちる箇所を確認する |
| 9-04 | 外部プロバイダーがメールを返さない場合の扱いを決めている | `mapProfileToUser` を読む |
| 9-05 | `emailVerified` に嘘を入れていない | 該当マッピングを読む |
| 9-06 | proxyの除外パターンが、1行ごとに理由を言える | 除外行を列挙して理由を書く |
| 9-07 | 公開が必要な口（OIDCメタデータ等）だけを除外している | `.well-known/` の到達性を確認する |
| 9-08 | 環境変数を倒す方向を、無いと何が壊れるかで決めている | 起動時throwと遅延初期化を使い分ける |
| 9-09 | IDトークンへ載せた状態が、どれだけ古くなりうるか把握した | 有効期間を確認する |
| 9-10 | トークンの値で通してよい操作と、引き直す操作を分けている | 重要操作の一覧を作る |
| 9-11 | RPを追加したときに更新が必要な箇所を書き出している | 信頼済みクライアントの定義箇所 |
| 9-12 | クライアントシークレットとトークンをハッシュ化して保存している | `storeClientSecret` / `storeTokens` |
